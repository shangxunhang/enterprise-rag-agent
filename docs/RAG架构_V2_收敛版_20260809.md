# 0. 文档目的

本文用于冻结当前 `rag-agent` 的 RAG V2 目标架构。

本文不是新的功能扩张计划，也不要求机械复现 Adaptive-RAG、CRAG、Self-RAG 三篇论文。

当前目标是：

> 从企业建设方案真实业务需求出发，吸收 Adaptive-RAG、CRAG、Self-RAG 的核心思想，形成一条职责清楚、资源受控、可审计、可评测、可后训练的企业 RAG 主链。

核心原则：

```text
不追求“用了多少 RAG 算法”
而追求：
为什么需要它？
什么时候触发？
解决什么问题？
什么时候停止？
失败后往哪里退？
如何证明有效？
```

本文重点冻结：

1. Adaptive-RAG-like：检索策略路由；
2. C-RAG-like：Evidence 质量控制与纠错；
3. Self-RAG-like：技术生成质量兜底；
4. Fact / Evidence 边界；
5. Research / Writer 回退关系；
6. 资源预算与停止条件；
7. Trace / Eval / 后训练数据闭环；
8. 与 Multi-Agent Runtime 的职责关系。

# 1. 当前业务问题

系统最终目标不是开放域问答，而是：

> 根据当前项目事实、客户材料、企业知识库和历史方案参考，生成一份建设方案正文型 DOCX。

当前业务有几个和普通 QA 不同的约束。

## 1.1 当前项目事实必须稳定

例如：

- 设备名称；
- 型号；
- 规格；
- 数量；
- 已确认金额；
- 总投资结果；
- 建设范围。

这些不是“检索答案”，而是当前项目事实。

因此：

```text
Fact != Evidence
```

RAG 不能通过历史文档、企业知识库或厂商资料覆盖当前项目事实。

## 1.2 Evidence 的作用是支持技术内容

Evidence 主要回答：

- 某种技术设计是否有依据；
- 某种能力是否成立；
- 某种架构、兼容性、安全性是否有技术支撑；
- 当前段落应该引用哪些技术依据。

它不能自行证明：

> “当前项目已经采用了某设备/某设计。”

除非当前项目事实明确这样规定。

## 1.3 历史方案只是参考，不是当前事实

历史项目可以用于：

- 章节组织；
- 表达方式；
- 技术思路；
- 通用方案结构。

但不能直接继承：

- 历史项目名称；
- 历史设备数量；
- 历史型号；
- 历史投资；
- 历史建设范围。

## 1.4 技术生成允许设计，但不允许造事实

Writer 可以基于事实和 Evidence 形成：

```text
supported_design
suggested_design
```

但不能把推导出来的设计写成：

```text
fact
```

建议内部区分：

```text
fact
supported_design
suggested_design
uncertain
```

`suggested_design` 可以进入正文，但必须保持可追溯，不允许在后续章节中自动升级为事实。

# 2. 权威性边界

当前项目事实 Authority 与 Evidence / Reference Authority 必须分开。

当前项目事实来源优先级冻结为：

```text
Excel / FactSnapshot
> 当前项目客户材料
```

技术内容可使用的 Evidence / Reference 来源按其合法用途治理，例如：

```text
Validated Vendor Evidence
企业知识库
历史方案
通用表达
```

`Verified Claim` 不是新的事实来源，也不拥有独立 Authority 层级。它只是经过验证后允许传播的 Claim，必须继承其原始 Fact / Evidence 的 `source_refs`、provenance 与 authority。

注意：该排序不是说所有信息都互相竞争。

更准确的原则是：

```text
同一事实域冲突时，原始权威源优先。
不同事实域各自使用其合法来源。
Claim 的验证状态不能提升其原始来源的 Authority。
```

例如：

```text
Excel 未描述“建设必要性”
```

不代表该部分为空。

此时当前项目客户材料可以成为建设必要性的事实来源。

# 3. RAG V2 总体架构

```text
                        Planner
                           |
                    Evidence Need
                           |
                           v
                 +--------------------+
                 |      Research      |
                 +--------------------+
                           |
               +-----------+-----------+
               |                       |
               v                       v
       Adaptive Router          Evidence Evaluator
       (Adaptive-RAG-like)       (C-RAG-like)
       下一步怎么找？             当前找得怎么样？
               |                       |
               +-----------+-----------+
                           |
                    EvidencePackage
                           |
                           v
                         Writer
                           |
                   Normal Generation
                           |
                           v
              Generation Trigger Eval
                           |
             +-------------+-------------+
             |                           |
           PASS                    技术内容质量不足
             |                           |
             v                           v
          Paragraph              Self-RAG-like
                                  fallback
                                      |
                           critique rewrite
                                      |
                           必要时 independent
                              regeneration
                                      |
                               best selection
                                      |
                     +----------------+----------------+
                     |                                 |
                 evidence_gap                  generation_quality
                     |                                 |
                     v                                 v
                  Research                         best candidate
                                                       |
                                                Review Report
```

三类 RAG 思想职责固定：

```text
Adaptive-RAG-like
= Retrieval Action Selection

C-RAG-like
= Evidence Quality / Coverage Control

Self-RAG-like
= Technical Generation Quality Fallback
```

三者不是三个串行“算法按钮”，而是分别服务于不同阶段。

# 4. 当前 Retrieval Baseline

V2 第一阶段不重新设计底层索引体系。

继续保留现有强 baseline：

```text
Dense + BM25
→ RRF
→ Parent-Child
→ Rerank
→ Context Pack
```

已有 Query Transformation：

```text
identity
multi_query
hyde
```

V2 的 Adaptive 层不以“动态切底层索引结构”为目标。

明确不做：

```text
根据 Query 动态切 HNSW / IVF
根据 Query 动态选择不同 Milvus Collection
为了 Adaptive 新增多套底层索引
为了面试制造大量 retrieval policy
```

Adaptive 的“策略”主要控制：

```text
是否继续检索
单轮还是多轮
是否 query expansion
是否 targeted retrieval
是否 rewrite query
下一轮聚焦什么 evidence gap
允许多少额外 retrieval computation
何时 stop
```

因此：

> Adaptive Routing 是 retrieval computation / action routing，不是底层索引工程无限扩展。

# 5. Planner 与 RAG 的边界

Planner 不负责真正检索，也不生成详细检索 Query。

`EvidenceRequirement` 的 canonical contract 由 RAG 层拥有。Planner 不定义第二份 Schema，只负责按照该 RAG contract 产生当前 Run / Section 的 runtime requirement instance：

```yaml
EvidenceRequirement:
  requirement_id: string
  section_id: string
  topic: string
  purpose: string
  importance: required | optional
  expected_source_types: []
```

这里的 Requirement 是生产运行时 Requirement；Evaluation 的 Gold Requirement 独立维护，不能从 Planner runtime output 反推 Gold。

Planner 输出的是：

> 当前 Section 需要什么 Evidence。

Research 决定：

> 怎么找到这些 Evidence。

因此职责链：

```text
Planner
定义 Evidence Need

Adaptive Router
选择 Retrieval Action

Retriever
真正执行

C-RAG Evaluator
判断结果够不够
```

# 6. Adaptive-RAG-like：检索策略路由

## 6.1 为什么需要 Adaptive

固定一种 retrieval strategy 的问题是：

- 简单 Evidence Need 可能被过度检索；
- 复杂技术主题可能一次检索不够；
- Query 表述不好时固定 query 会持续失败；
- Evidence Gap 已经非常明确时，继续宽泛检索浪费 Tool Call；
- 一种策略在所有 Query 上不一定都是成本/质量最优。

因此需要：

> 根据当前 Evidence Need + 当前 Evidence State + Retrieval History，动态决定下一步检索动作。

## 6.2 与原 Adaptive-RAG 的关系

原论文核心思想可以抽象为：

```text
Query
→ 判断任务复杂度
→ 分配不同 retrieval computation
```

本项目不机械照搬：

```text
No Retrieval / Single-step / Multi-step QA
```

而做业务化 adaptation：

```text
Evidence Need
+ Current Evidence State
+ Retrieval History
→ Retrieval Action
```

原因：

企业建设方案不是 open-domain QA。

系统核心目标不是“给一个答案”，而是获得：

- 可追溯 Evidence；
- Evidence Requirement Coverage；
- Citation / Claim Binding；
- 可控的检索成本。

## 6.3 Router 模型

V2 目标：

```text
Qwen2.5-3B 或同级小模型
```

Router 第一阶段：

```text
Prompt + Structured Output
```

不先微调。

稳定后再基于 Trace 构建训练集。

## 6.4 Router 输入

建议最小输入：

```yaml
RetrievalRoutingInput:
  section_id: string
  evidence_requirements: []
  current_coverage: []
  evidence_gaps: []
  conflicts: []
  previous_actions: []
  no_gain_rounds: integer
  remaining_budget: {}
```

禁止把全部历史正文塞给 Router。

Router 只需要看完成决策所需状态。

## 6.5 Action Space

V2 第一阶段保持克制：

```text
single_retrieval
expanded_retrieval
rewrite_query
multi_query
focused_retrieval
iterative_retrieval
stop
```

具体可以映射到现有：

```text
identity
multi_query
hyde
hybrid retrieval baseline
corrective retrieval
```

Action Space 不应无限增加。

## 6.6 Router 输出

```yaml
RetrievalDecision:
  action: string
  target_requirements: []
  query_hint: string | null
  confidence: float
  reason_code: string
  expected_gain: string | null
```

`reason_code` 用于 Trace / Eval。

不保存模型私有 chain-of-thought。

## 6.7 Router 权限

Router 只负责：

> 选择下一步 retrieval action。

Router 不负责：

- 直接执行检索；
- 修改 EvidencePackage；
- 判定最终 Evidence 是否正确；
- 修改 Workflow State；
- 无限增加预算；
- 决定最终文档是否可发布。

## 6.8 预算

确定性系统必须限制：

```yaml
max_research_rounds_per_section: 3
max_queries_per_round: 3
max_tool_calls_per_section: 9
max_no_gain_rounds: 2
```

具体数值后续可通过 Eval 校准。

原则不变：

> Router 可以建议继续，但不能突破硬预算。

## 6.9 Shadow Router 演进

第一步不建议直接把 heuristic router 删除。

Shadow Router 的前置条件冻结为：

```text
RetrievalDecision Trace 可记录
RetrievalOutcome 可记录
Evidence Coverage 可计算
当前 heuristic baseline 可复现
```

满足前置后采用：

```text
Heuristic Router → production baseline
3B Router        → shadow decision
```

记录：

```text
baseline_strategy
shadow_strategy
disagreement
actual_outcome
```

没有 Trace / Outcome Capture 与可复现 Baseline 时，不启动 Shadow Router。验证 3B 真有收益以后，再逐步切换。

# 7. C-RAG-like：Evidence Quality Control

## 7.1 为什么需要独立 Evaluator

Adaptive Router 回答：

> 下一步怎么找？

但它不能同时承担：

> 当前 Evidence 到底够不够？

这两个问题必须分开。

否则会出现：

```text
Router 自己决定策略
→ 自己判断策略成功
→ 自己决定停止
```

形成自证闭环。

因此 Research 内部需要独立 Evidence Evaluator。

## 7.2 两级 Evidence Evaluation

V2 冻结为两级。

### Level 1：单条 Evidence Quality

对每条 Evidence 判断：

```text
relevance
support
source_quality
conflict
```

结构化输出：

```yaml
EvidenceAssessment:
  evidence_id: string
  relevant: bool
  support_level: none | weak | partial | strong
  source_quality: low | medium | high
  conflict_refs: []
  accepted: bool
  reason_code: string
```

### Level 2：Evidence Package Coverage

不是看单条好不好，而是看 Planner 要求是否覆盖。

```yaml
EvidenceCoverage:
  covered_requirements: []
  partially_covered_requirements: []
  missing_requirements: []
  conflicts: []
  overall_status:
    - sufficient
    - insufficient
    - conflicted
```

`overall_status` 只描述 Evidence 当前质量/覆盖状态，不表达为什么 Research 停止。

## 7.3 C-RAG-like 的核心含义

不是：

> 起一个名字叫 C-RAG Evaluator。

真正要实现的是：

```text
Retrieve
→ Evaluate
→ 发现质量低 / coverage gap
→ Correction / Targeted Retrieval
→ Re-evaluate
```

这才是 corrective retrieval 思想。

## 7.4 Correction 类型

Evidence 不足时，Evaluator 只说明问题：

```text
missing_requirement
low_relevance
weak_support
source_quality_low
conflict
```

它不直接选择下一步动作。

由 Adaptive Router 根据 Evaluator 输出决定：

```text
rewrite_query
multi_query
focused_retrieval
iterative_retrieval
stop
```

因此：

```text
Evaluator = What state are we in?
Router    = What should we do next?
```

## 7.5 Research 停止条件

停止条件必须至少包含：

```text
Evidence sufficient
预算耗尽
连续 no-gain
明确 conflicted 且继续检索无收益
达到 max rounds
```

最终必须分别记录 Evidence 状态与停止原因：

```yaml
evidence_status:
  - sufficient
  - insufficient
  - conflicted

stop_reason:
  - evidence_sufficient
  - no_gain
  - budget_exhausted
  - max_rounds
  - unrecoverable_conflict
```

`exhausted` 不再作为 Evidence 状态。预算耗尽、达到最大轮数或连续 no-gain 都属于 `stop_reason`。

# 8. EvidencePackage

Research 最终不把全部 Tool Trace 交给 Writer。

输出受控 EvidencePackage。

`EvidencePackage` 的 canonical contract 由 RAG 层拥有；Agent / Writer 侧只消费该 contract，不定义第二份 EvidencePackage Schema。

```yaml
EvidencePackage:
  section_id: string
  evidence_status: sufficient | insufficient | conflicted
  stop_reason: string | null
  requirements: []
  accepted_evidence: []
  rejected_evidence_summary: []
  coverage: {}
  conflicts: []
  missing_requirements: []
  research_rounds: integer
  tool_calls: integer
  package_hash: string
```

Writer 只读取：

- 当前项目 Fact；
- 当前 SectionPlan；
- EvidencePackage；
- 必要 Verified Claims；
- 当前写作上下文。

Writer 不读取完整 Research reasoning。

# 9. Writer 与 Research 的边界

Writer 无主动 Retrieval 权限。

主流程：

```text
Research
→ EvidencePackage
→ Writer
```

如果 Writer 判断材料不足：

```text
WriterResult:
  status = need_more_evidence
  missing_evidence_topics = [...]
```

然后：

```text
Supervisor / Section Graph
→ Research
```

禁止：

```text
Writer 直接调用 Milvus
Writer 自己追加 Search Tool
Writer 一边写一边无限检索
```

原因：

- 难以审计；
- 预算失控；
- Evidence 状态不稳定；
- RAG 和 generation 职责混乱。

# 10. Section Strategy 与 RAG 使用范围

Planner 的 Section Strategy 建议冻结为：

```text
source_adapt
rag_generate
technical_generate
skip
```

## 10.1 source_adapt

适合：

- 项目背景；
- 建设必要性；
- 当前项目已有材料改写；
- 模板化强、技术推理弱的章节。

通常：

```text
当前项目材料
+ 少量事实
→ normal generation
```

不默认启用复杂 Adaptive / Self-RAG 路径。

## 10.2 rag_generate

适合：

- 需要知识库依据；
- 但不属于复杂技术设计的章节。

使用：

```text
Research
→ Adaptive / C-RAG-like
→ normal generation
```

## 10.3 technical_generate

适合：

- 高可用设计；
- 虚拟化；
- 调度；
- 迁移；
- 网络技术设计；
- 安全设计；
- 资源组织；
- 架构逻辑。

使用完整链：

```text
Research
→ Adaptive / C-RAG-like
→ normal generation
→ Trigger Eval
→ 必要时 Self-RAG-like fallback
```

## 10.4 普通事实段落

即使属于技术章节，如果只是：

> 当前项目配置 16 台服务器。

也不需要 Self-RAG。

Self-RAG 应用于高价值技术推理内容，而不是整个 technical section 无差别触发。

# 11. Self-RAG-like：技术生成质量兜底

## 11.1 定位

V2 不把 Self-RAG 作为默认生成算法。

冻结定位：

> Self-RAG-like 是技术生成的质量兜底 / escalation path。

普通路径：

```text
Technical Paragraph Task
→ Writer normal generation
→ Generation Trigger Eval
→ PASS
```

只有第一次普通生成不够好时：

```text
进入 Self-RAG-like fallback
```

## 11.2 为什么不默认 best-of-N

默认多 candidate 会导致：

- GPU 成本高；
- latency 大；
- Context 重复消耗；
- 大多数简单段落没有必要。

因此选择：

```text
先单次生成
失败才增加 test-time compute
```

## 11.3 禁止 Evidence 子集组合爆炸

不采用：

```text
Facts + E1 + E2
Facts + E1 + E3
Facts + E2 + E3
...
```

原因：

EvidencePackage 中不同 Evidence 常常是互补关系，不是互斥候选。

任意组合 Top-K Evidence：

- 计算量快速膨胀；
- 破坏完整 Evidence Coverage；
- 不符合当前业务。

Writer 应基于一个已治理的 EvidencePackage 生成。

---

# 12. Self-RAG Trigger Metrics

这里必须区分两套指标。

第一套：

> 是否进入 Self-RAG-like。

第二套：

> Self-RAG-like 运行后，选哪个 candidate / 什么时候停。

不能混为一套。

## 12.1 Trigger Metrics

第一次普通生成后，用低成本 Generation Evaluator 判断：

```text
technical_completeness
technical_coherence
task_relevance
specificity
clarity
generation_risk
critical_issue
```

示意质量分：

```text
quality_score =
0.30 * technical_completeness
+ 0.25 * technical_coherence
+ 0.20 * task_relevance
+ 0.15 * specificity
+ 0.10 * clarity
```

注意：

> 权重和阈值现在只是设计占位，不在架构阶段拍脑袋冻结。

后续必须用真实建设方案 Eval Set 校准。

触发规则示意：

```text
quality_score < threshold
OR critical_issue = true
OR technical_completeness < threshold
→ Self-RAG-like
```

关键原则：

> Trigger Eval 必须尽量便宜，否则为了判断“要不要省算力”先花掉大量算力，本末倒置。

# 13. Self-RAG-like 执行路径

冻结选择：方案 C。

```text
candidate_1
   |
Generation Evaluator
   |
质量不足
   v
Critique
   |
Targeted Rewrite
   v
candidate_2
   |
Generation Evaluator
   |
仍不足
   v
Independent Regeneration
   |
candidate_3
   |
Candidate Selection
```

也就是：

1. 第一次失败：优先 critique-guided rewrite；
2. 第二次仍失败：允许一次独立 regeneration；
3. 比较候选，选当前最好结果；
4. 达到硬预算必须停止。

不允许无限循环。

建议：

```yaml
max_generation_attempts: 3
```

# 14. Generation Evaluator

## 14.1 为什么独立于 Writer

V1 Writer 并不是一个真正训练了 reflection token 的 Self-RAG Generator。

如果 Writer 自己写、自己审、自己宣布通过：

```text
author == auditor
```

容易自证。

因此 V2 使用：

> 独立 Generation Evaluator。

它是 Writer pipeline 内部 model component，不新增业务 Agent。

## 14.2 Evaluator 输出

```yaml
GenerationEvaluation:
  quality_score: float
  technical_completeness: float
  technical_coherence: float
  task_relevance: float
  specificity: float
  clarity: float
  critical_issue: bool
  root_cause:
    - pass
    - generation_quality
    - evidence_gap
    - unresolved_design
  critique: []
  recommended_action:
    - accept
    - critique_rewrite
    - independent_regenerate
    - research_more
    - stop_and_review
```

Evaluator 给出建议。

真正 Workflow 路由仍由 deterministic control plane 执行。

# 15. Self-RAG Selection / Stop Metrics

进入 Self-RAG-like 后，指标目标发生变化。

现在要回答：

> 哪个 candidate 更好？还有没有必要继续花算力？

主要使用：

```text
absolute_quality
quality_delta
critical_issue
attempt_count
remaining_budget
```

例如：

```text
candidate_1 = 0.68
candidate_2 = 0.84
```

接受 candidate_2。

如果：

```text
candidate_2 = 0.82
candidate_3 = 0.83
```

提升很小，不继续扩展。

因此停止规则：

```text
达到 PASS threshold
OR 改进幅度过小
OR 达到 max attempts
OR budget exhausted
```

---

# 16. Self-RAG 失败后的回退

Self-RAG-like 失败后，必须先做 root cause attribution。

冻结三类：

```text
generation_quality
evidence_gap
unresolved_design
```

## 16.1 generation_quality

说明 Evidence 本身够，问题只是生成质量。

允许：

```text
critique rewrite
independent regeneration
candidate selection
```

不允许回 Research。

## 16.2 evidence_gap

只有明确判定为：

```text
输入给 Writer 的 Evidence 不足
```

才允许：

```text
Writer / Generation Evaluator
→ Supervisor / Section Graph
→ Research
→ Adaptive Router
→ Retrieval
→ C-RAG Evaluator
→ Writer
```

## 16.3 unresolved_design

Evidence 基本够，但设计本身存在工程判断空间，模型在预算内仍不能稳定给出可靠答案。

处理：

```text
选择当前最好 candidate
+ Review Report 标记
```

不无限生成。

---

# 17. 跨阶段 Backtrack Budget

RAG ↔ Writer 不能无限循环。

建议 V2 第一阶段：

```yaml
max_evidence_backtracks_per_section: 1
```

或者最多 2 次，后续用数据校准。

原则：

> 回 Research 是高成本动作，只对明确 evidence_gap 开放。

达到预算后：

```text
best available result
+ review flag
```

# 19. RAG 与 Verifier 的边界

C-RAG Evidence Evaluator 不是最终 Verifier。

它只关心：

> Research 结果是否能支撑后续生成。

Generation Evaluator 也不是最终 Verifier。

它只关心：

> 技术生成质量是否值得额外算力。

最终 Verifier 关心：

- Fact consistency；
- Evidence / Citation consistency；
- Claim Binding；
- Section completeness；
- cross-section consistency；
- obvious technical risk。

因此：

```text
Evidence Evaluator
!= Generation Evaluator
!= Verifier
```

避免一个万能 Evaluator 包揽所有职责。

# 20. Deterministic Precheck 与 LLM Evaluation

为了成本和稳定性，明显可规则化的问题先规则判断。

例如：

- 设备数量冲突；
- 型号冲突；
- 金额冲突；
- 当前项目不存在的设备；
- 旧项目名称；
- Evidence ID 不存在；
- Citation Binding 无效。

这些不应该先调用大模型。

LLM 主要用于：

- semantic support；
- technical completeness；
- design coherence；
- relevance；
- evidence gap attribution。

原则：

```text
能确定性判断的，不使用 LLM。
```

# 23. Adaptive Router 后训练闭环

## 23.1 3B 不是 Ground Truth

重要原则：

> 3B Router 的建议不能直接等于最优标签。

正确训练数据闭环：

```text
3B Teacher / Prompt Router 建议
+
不同策略实际运行 Outcome
+
Retrieval / C-RAG / Generation / Cost Eval
↓
Empirical Best Strategy
↓
Training Label
```

否则只是：

> 模仿 3B。

不能证明 Router 优化了真实系统效用。

## 23.2 Router Dataset

建议记录：

```yaml
RouterTrainingSample:
  evidence_need: {}
  current_state: {}
  previous_actions: []
  candidate_actions: []
  teacher_action: string
  strategy_outcomes: []
  optimal_action: string
  label_source: empirical_eval
  label_confidence: float
```

## 23.3 演进顺序

```text
Decision Trace + Retrieval Outcome Capture
↓
V1 heuristic baseline
↓
V2 3B shadow router
↓
strategy outcome comparison
↓
empirical labels
↓
3B / smaller router fine-tuning
↓
A/B vs heuristic / prompt router
```

这是优先于“为了训练而训练”的路线。

# 24. Generation Evaluator / Writer 后训练

如果后续进入算法岗准备，可以继续训练：

```text
Generation Evaluator
Writer / Technical Generator
```

但优先级低于 Adaptive Router。

原因：

Router 的任务更干净：


更容易：

- 量化 baseline；
- 评估 SFT 前后提升；
- 做错误分析。

Writer / Evaluator 的监督标准更复杂，后续再做。

# 26. Tool Gateway 边界

# 27. Context Engineering 与 RAG 的关系

RAG Context 不等于 Agent 全部 Context。

Writer 的完整上下文来自：

```text

+ SectionPlan
+ EvidencePackage
+ Verified Claims
+ Writer Progress
+ unresolved Issues
+ compressed local context
```

ContextCompiler 决定什么真正进入 LLM。

RAG 只提供其中：

```text

```


# 28. Resource Control

RAG V2 所有智能循环都必须有硬预算。

## Research

```text
max rounds
max queries
max tool calls
max no-gain rounds
```

## Self-RAG-like

```text
max generation attempts
max independent regeneration
max evidence backtrack
```

## Evaluator

尽量：

```text
cheap trigger eval
```

进入增强路径后才允许更重的评估。

原则：

> Test-time compute 必须按内容价值动态分配，而不是所有段落平均烧算力。

# 29. 当前明确不做

V2 RAG 不做：

- 无限增加 retrieval strategy；
- 动态切大量底层索引结构；
- 为了 Adaptive 建第二套向量库；
- Writer 自由检索；
- Self-RAG 全文默认 best-of-N；
- Top-K Evidence 子集组合搜索；
- 无限 reflection；
- 无限 Research ↔ Writer backtrack；
- 一个万能 Evaluator；
- 机械声称“完整复现论文”；
- 没有 benchmark 就直接微调所有小模型。

# 30. 推荐实施顺序

不要求一次重写 RAG。

```text
R0  保留当前强 Retrieval Baseline
    ↓
R1  冻结 RAG-owned EvidenceRequirement / EvidencePackage Contract
    ↓
R2  C-RAG-like Evidence Evaluator 两级评价
    ↓
R3  Research bounded loop + no-gain stop
    ↓
R4  Router Decision Trace + Retrieval Outcome Capture
    ↓
R5  冻结可复现 heuristic baseline
    ↓
R6  3B Adaptive Router Shadow Mode
    ↓
R7  Strategy Outcome Eval
    ↓
R8  technical_generate Trigger Evaluator
    ↓
R9  Self-RAG-like critique rewrite / regeneration fallback
    ↓
R10 evidence_gap backtrack + hard budget
    ↓
R11 真实建设方案 E2E + A/B Benchmark
    ↓
R12 可选 Router SFT / Eval
```

顺序原因：

> 先把 Evidence 状态和 Eval 做清楚，再让 3B Router 接管策略；先有普通技术生成 baseline，再增加 Self-RAG 兜底。

# 31. 必须通过的验收场景

## RAG-01 简单 Evidence Need

一次检索已经覆盖全部 required Evidence。

预期：

```text
C-RAG status = sufficient
Adaptive Router = stop
```

不额外检索。

## RAG-02 Evidence Gap

第一次检索缺少高可用技术依据。

预期：

```text
C-RAG missing_requirement
→ Adaptive Router focused_retrieval
→ coverage 增加
```

## RAG-03 No Gain

连续检索没有新增有效 Evidence。

预期：

```text
no_gain_rounds 达阈值
→ evidence_status = insufficient
→ stop_reason = no_gain
```

不无限检索。

## RAG-04 Conflict

两个来源对同一技术能力产生冲突。

预期：

```text
conflict 被显式记录
不能静默合并
Router 根据状态决定补证据或停止
```

## RAG-05 Fact Authority

历史方案写 6 台服务器，FactSnapshot 写 16 台。

预期：

```text
最终 accepted 正文只能把 16 台作为当前项目事实
```

## GEN-01 普通技术生成通过

第一次 technical_generate quality 足够。

预期：

```text
Self-RAG-like 不触发
```

## GEN-02 Critique Rewrite

第一次生成技术完整性不足。

预期：

```text
Trigger Eval 失败
→ critique-guided rewrite
→ candidate_2
```

## GEN-03 Independent Regeneration

candidate_2 仍不达标。

预期：

```text
最多再 independent regeneration 一次
→ candidate selection
→ stop
```

## GEN-04 Evidence Gap Backtrack

Generation Evaluator 明确：

```text
root_cause = evidence_gap
```

预期：

```text
允许回 Research
```

## GEN-05 Generation Quality 不回检索

```text
root_cause = generation_quality
```

预期：

```text
只能 rewrite / regenerate
不能调用 Research
```

## GEN-06 Unresolved Design

预算耗尽后仍存在工程判断不确定性。

预期：

```text
选 best candidate
+ Review Report
```

# 33. 面试技术主轴

推荐陈述：

> 我没有把 Adaptive-RAG、CRAG、Self-RAG 按论文形式机械串联，而是先从建设方案生成的业务约束拆职责。Adaptive-RAG 的核心思想被用于 retrieval computation routing，由 3B Router 根据 Evidence Need、当前覆盖和历史检索状态选择下一步检索动作；CRAG 的核心思想用于 Evidence Quality Control，对单条证据和整个 Evidence Package 做两级评价，并根据 coverage gap 触发 corrective retrieval；Self-RAG 的 reflection 思想只用于高价值技术设计段落，普通生成先走低成本路径，质量不足才动态增加 test-time compute，通过 critique rewrite、有限独立 regeneration 和 candidate selection 做兜底。整个 Research/Generation 循环都有硬预算，并将 Router Decision、Evidence Outcome、Generation Evaluation、成本和延迟写入 Trace，用于 benchmark 和后续小模型训练。

必须明确：

```text
这是 paper-inspired enterprise adaptation
不是 strict reproduction
```

# 34. Definition of Done

RAG V2 只有同时满足以下条件才算完成。

## Retrieval Baseline

- Dense + BM25 + RRF + Parent-Child + Rerank 保持稳定；
- 不为了 Adaptive 无限增加底层索引策略。

## Adaptive

- 3B Router 有强类型输入输出；
- Router 只做 strategy/action selection；
- 有 hard budget；
- 有 Shadow / A-B evidence；
- 有 Decision Trace。

## C-RAG-like

- 单条 Evidence Quality 评价；
- Evidence Requirement Coverage 评价；
- `evidence_status = sufficient / insufficient / conflicted` 语义清晰；
- `stop_reason` 与 Evidence 状态分离；
- no-gain 能以明确 `stop_reason` 停止；
- correction 路径真实执行。

## Writer / Self-RAG-like

- Writer 无 Retrieval 权限；
- 普通技术段落默认单次生成；
- Trigger Metrics 与 Selection/Stop Metrics 分离；
- critique rewrite 可运行；
- independent regeneration 有硬次数上限；
- evidence_gap 才允许回 Research；
- unresolved_design 最终进入 Review Report。

## Fact / Evidence

- Fact != Evidence；
- Excel / FactSnapshot 事实权威不被 RAG 覆盖；
- 历史方案不成为当前事实；
- EvidencePackage 可追溯。

## Trace / Eval

- Router Decision 可追踪；
- Retrieval Outcome 可追踪；
- C-RAG coverage 可追踪；
- Self-RAG Trigger / attempts / selection 可追踪；
- 至少有一组 Retrieval A/B；
- 至少有一组 Generation A/B。

## Resource

- Research loop 有硬预算；
- Self-RAG loop 有硬预算；
- RAG ↔ Writer backtrack 有硬预算；
- 不出现无限循环。

# 35. 最终冻结原则

1. RAG 的目标不是堆算法，而是稳定提供可用 Evidence。
2. Fact 与 Evidence 永远分开。
3. 当前项目硬事实以 FactSnapshot 为 authority。
4. 历史方案只作为结构、表达和技术参考。
5. Adaptive-RAG-like 解决“下一步怎么找”。
6. C-RAG-like 解决“当前找得怎么样”。
7. Self-RAG-like 解决“高价值技术生成质量不够时怎么办”。
8. 三者职责不重叠，不做万能 Router / Evaluator。
9. 底层强 Retrieval Baseline 保持稳定，不为 Adaptive 无限扩索引策略。
10. Writer 不拥有主动检索权。
11. Research 输出受控 EvidencePackage，不把全部 Tool Trace 交给 Writer。
12. Self-RAG-like 不是默认主链，而是技术生成质量兜底。
13. 普通事实段落不使用 Self-RAG。
14. 默认单 candidate，失败才增加 test-time compute。
15. 不做 Evidence 子集组合爆炸。
16. Trigger Metrics 与 Selection / Stop Metrics 分离。
17. 只有 evidence_gap 才允许 Generation 回 Research。
18. 所有循环都有 hard budget。
19. 3B Teacher 不是 Ground Truth；训练标签最终依赖真实 Strategy Outcome。
20. 所有关键决策必须进入 Trace，并能通过独立 Evaluation Foundation 证明改造价值。
21. Evidence 状态只描述证据质量/覆盖状态；预算耗尽、no-gain、max rounds 等只进入 `stop_reason`。
22. `Verified Claim` 不成为新的 Fact Authority，必须继承原始 Fact / Evidence provenance。
23. EvidenceRequirement / EvidencePackage 的 canonical contract authority 属于 RAG；Agent 只生产/消费兼容实例。
24. 面试叙事强调论文思想的企业化 adaptation，而不是机械复现。
25. 后续新增 RAG 能力必须回答：它解决了现有哪个可量化问题，否则不进入 V2。
