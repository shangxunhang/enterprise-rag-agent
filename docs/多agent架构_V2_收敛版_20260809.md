# 1. 系统定位

## 1.1 业务目标

系统只解决一个清晰问题：

> 根据当前项目事实、客户材料、历史方案结构参考和企业知识库，辅助生成一份建设方案正文型 Word 文档。

当前建设方案只是验证 Agent-RAG 基座的第一个业务场景，不要求一次实现所有文档、表格、图纸和工程计算能力。

## 1.2 最终输出

V2 的核心最终输出是：

```text
结构化文本型 DOCX

封面 / 标题
章节
小节
正文 Paragraph
必要的审查标记或 Review Report
```

不把复杂富媒体输出作为当前目标。

明确不由系统自动生成：

- 投资估算表；
- 报价表；
- 设备清单表；
- CAD；
- 机架图；
- 端口分配表；
- 布线表；
- 自动拓扑图；
- 复杂图表；
- 全量 Word 样式复刻。

投资估算等表格继续由现有确定性业务流程产生，最终由人工粘贴进 Word。系统可以读取已经确认的投资结果，并在正文中引用，但不得重新计算或自行生成该表。

## 1.3 基座与扩展的边界

```text
                 Agent-RAG 基座
                       |
     Fact / RAG / Agent / Memory / Verify
                       |
                 Text DOCX Output
                       |
          ---------------------------
          Future Optional Extensions
          表格 / 拓扑 / CAD / 其他文档
```

当前只实现一个上层业务场景来证明基座有效，不为了证明“可扩展”而把所有扩展都实现一遍。

# 2. 总体设计原则

## 2.1 功能做窄，技术做深

本项目后续判断一个需求是否进入 V2，只问两个问题：

1. 它是否直接满足建设方案正文生成？
2. 它是否显著增加 RAG 或 Agent Runtime 的技术深度？

如果只是增加一种输出能力，默认不进入 V2。

## 2.2 Agent 做认知工作，Service 做确定性工作

Agent 负责：

- 理解；
- 规划；
- 语义判断；
- 检索策略选择；
- 文本生成；
- 语义验证。

确定性 Service / Graph 负责：

- Excel 解析；
- 状态迁移；
- DAG 调度；
- 权限；
- Retry；
- Budget；
- Checkpoint；
- Idempotency；
- Artifact 持久化；
- DOCX 装配；
- Hard Gate；
- 发布。

禁止仅因为某能力“可以包装成 Agent”就新增 Agent。

## 2.3 四个业务 Agent 足够

V2 只保留：

```text
PlannerAgent
ResearchAgent
WriterAgent
VerifierAgent
```

明确不新增：

- TableAgent；
- MemoryAgent；
- CriticAgent；
- CitationAgent；
- ReflectionAgent；
- ResearchManagerAgent；
- DocumentManagerAgent；
- 独立 RouterAgent。

Adaptive Router、C-RAG Evaluator、Generation Evaluator 都属于 Agent 内部的 Model Component / Capability，不升级为新的业务 Agent。

# 4. 输入、事实与 Run 边界

## 4.1 Excel 只由确定性 Parser 解析

Agent 不直接“看 Excel 单元格然后猜含义”。

```text
Excel
  ↓
ExcelParser Service
  ↓
FactSnapshot
  ↓
Agent
```

`FactSnapshot` 至少覆盖当前项目中实际需要的：

- 设备名称；
- 型号；
- 规格；
- 数量；
- 已确认价格或投资结果；
- 软件 / 硬件分类；
- 密码、量子、安全等项目事实；
- 建设范围。

若 Excel 本身不包含项目背景、必要性、现状、目标等内容，则这些事实由当前项目客户材料提供。

## 4.2 事实权威关系

原则不是“所有问题 Excel 都最高”，而是：

> Excel 对其覆盖的项目事实拥有最终 authority；Excel 没覆盖的项目事实由当前项目材料提供。

历史方案只能提供：

- 结构；
- 表达；
- 技术组织方式；
- 方案思路参考。

历史方案不能把旧项目事实带入当前项目。

企业知识库、标准、厂商材料提供的是 Evidence / Technical Basis，不自动成为当前项目 Fact。

核心区分：

```text
Fact != Evidence
```

## 4.3 每次完整输入形成独立 Run

V2 取消复杂的跨 Run 增量更新模型。

```text
完整输入提交
  ↓
Run-001
  ↓
Run 完成并关闭
```

如果用户随后修改 Excel、模板或项目材料：

```text
新完整输入
  ↓
Run-002
```

而不是：

```text
修改旧 Run
→ 全局 stale propagation
→ Major / Minor Version 影响图
```

V2 只要求同一 Run 内的生命周期、恢复和一致性。

## 4.4 Run 冻结

Run 创建时冻结：

```text
input_snapshot_id
fact_snapshot_id
template_version
knowledge/index_version
model_config_version
prompt_version
workflow_version
```

运行中的 Agent 不读取“当前最新可变文件”，只能读取本 Run 冻结的引用。

# 5. Supervisor 与控制面

## 5.1 保留唯一现有 Supervisor

生产主链继续是：

```text
MainlineApplicationService
→ SupervisorAgent
→ EnterpriseDocumentWorkflowEngine
→ SectionExecutionGraph
```

不增加第二个 Supervisor，不恢复 Standalone `WorkflowOrchestrator`。

## 5.2 Deterministic Controller 是主控制面

以下状态不需要询问 LLM：

```text
research.sufficient       → Writer
need_more_evidence        → Research
writer.completed          → Verifier
repairable                → Writer Repair
budget exhausted          → Stop / Degrade
hard dependency completed → Unlock downstream
Hard Gate FAIL             → Do not publish
```

State Machine、DAG、Retry、Budget、Checkpoint、权限必须保持确定性。

## 5.3 Supervisor LLM 只作为可选 fallback

如果后续 Trace 证明存在真实、频繁的高层语义歧义，可以给 Supervisor 增加一个语义决策 LLM。

它只允许处理：

- 多个专业 Agent 结果发生语义冲突；
- 现有错误码无法判断主要根因；
- 规则无法覆盖的新型高层语义状态。

它不能：

- 推翻明确的专业 Agent 结论；
- 直接修改 State；
- 直接执行 Tool；
- 决定 Retry/Budget；
- 替代 Research/Writer/Verifier 自己的专业职责。

输出必须是结构化决策，并由 Controller 校验 allowlist 后执行。

V2 不要求为了“Agent 一定要有 LLM”而强行启用 Supervisor LLM；有真实语义需求再启用。

# 6. 四个业务 Agent

# 6.1 PlannerAgent

Planner 负责“这个建设方案应该怎么执行”，而不是自由发明整篇文档结构。

输入：

- TemplateSchema；
- FactSnapshot；
- 当前项目材料摘要；
- SourceInventory；
- RunContext。

核心输出：

```yaml
SectionPlan:
  section_id: string
  section_title: string
  applicable: bool
  section_strategy:
    - source_adapt
    - rag_generate
    - technical_generate
    - skip
  required_facts: []
  evidence_topics: []
  dependencies: []
  consistency_refs: []
  risk_hints: []
  allow_suggested_design: bool
  parallel_group: string | null
```

职责：

- 章节适用性；
- Section Strategy；
- 所需 Fact；
- Evidence Topics；
- Hard Dependency；
- Cross-section consistency reference；
- 并行组；
- 风险提示。

不负责：

- 具体 Query；
- 检索策略；
- Chunk 选择；
- 正文生成；
- 事实验证；
- 文档装配。

`human_review` 不再是正常 Section Strategy。

# 6.2 ResearchAgent

Research 只解决一个问题：

> 当前 Section 写作需要的证据是否已经足够、可靠、可追溯？

## 6.2.1 Research 主循环

```text
SectionPlan.evidence_topics
      ↓
Current Evidence State
      ↓
Adaptive Retrieval Router
      ↓
Retrieval Action
      ↓
ToolGateway → RAG
      ↓
Evidence Candidates
      ↓
C-RAG-like Evidence Evaluator
      ↓
Evidence Package Coverage
      ↓
Enough?
 ├─ No  → Router → next retrieval action
 └─ Yes → EvidencePackage Commit
```

## 6.2.2 Adaptive-RAG-like：策略选择

项目不机械复现 Adaptive-RAG 的 `No Retrieval / Single / Multi-step QA`。

项目使用其核心思想：

> 根据当前任务和检索状态动态分配 retrieval computation。

Router 负责选择下一步 Action，例如：

```text
keyword
vector
hybrid
rewrite
multi_query
targeted_search
stop
```

底层强 baseline 仍然可以固定为现有 Dense + BM25 + Fusion + Parent/Child + Rerank；V2 不为了“Adaptive”动态切换所有底层索引结构。

目标 Router 为小模型（约 3B）语义路由器，但生产替换前先通过 Shadow / A-B / Trace 验证是否优于 deterministic baseline。

Router 只决策，不执行 Tool，不控制全局循环。

## 6.2.3 C-RAG-like：证据质量控制

Evidence Evaluator 与 Router 分离。

第一层：单条 Evidence 评价：

```text
relevance
support
source_quality
conflict
```

第二层：EvidencePackage 覆盖评价：

```text
covered_requirements
missing_requirements
conflicts
overall_status
```

输出 Evidence 状态：

```text
sufficient
insufficient
conflicted
```

Evaluator 只回答“现在证据状态怎么样”，不回答“下一步调用什么 Tool”。预算耗尽、no-gain、max rounds 等必须单独记录为 `stop_reason`，不能编码成 Evidence 状态。

## 6.2.4 Research 硬预算

V2 必须有限循环，例如：

```text
max_research_rounds_per_section = 3
max_no_gain_rounds = 2
max_tool_calls_per_section = configurable hard limit
```

停止条件：

- Evidence sufficient；
- no-gain；
- conflicted 且继续检索无收益；
- budget exhausted；
- max rounds。

停止后必须同时保留：

```text
evidence_status
stop_reason
```

Research 不得无限自主探索。

# 6.3 WriterAgent

Writer 只负责生成和局部修订，不拥有检索权。

输入：

```text
SectionPlan
FactSnapshot subset
EvidencePackage
Current Section Memory
Verified Claims from authorized dependencies
Historical structure/style reference
```

## 6.3.1 Fact 与 Design 分离

Writer 可以做技术设计，但不能编造当前项目事实。

内部至少区分：

```text
fact
supported_design
suggested_design
uncertain
```

例如当前输入只说明“建设 16 台服务器”，Writer 可以基于知识和标准组织高可用设计方案，但不能把一个没有来源的型号、数量或已确定部署方式写成当前项目既定事实。

`suggested_design` 可以进入正文，但不能在后续循环中自动升级成 Fact。

## 6.3.2 Paragraph 级生成

```text
Paragraph Task
   ↓
ContextCompiler
   ↓
Writer
   ↓
Paragraph Artifact Commit
   ↓
Claim Candidate / Binding Hint
   ↓
Precheck
```

Paragraph 是最小生成、提交、修订和恢复原子。

## 6.3.3 Self-RAG-like 只做技术生成兜底

不是所有章节都走 Self-RAG。

```text
source_adapt       → normal generation
rag_generate       → normal RAG generation
technical_generate → normal generation first
                       ↓
                  low-cost trigger eval
                       ↓
                  pass? yes → done
                       ↓ no
                  Self-RAG-like fallback
```

Self-RAG-like 只用于高价值技术设计内容，例如：

- 高可用；
- 虚拟化；
- 调度；
- 迁移；
- 网络设计；
- 安全设计；
- 技术架构逻辑。

纯事实复述不需要 Self-RAG。

## 6.3.4 Self-RAG-like 路径

采用已经冻结的 C 路径：

```text
candidate_1
→ Generation Evaluator
→ critique
→ targeted rewrite candidate_2
→ evaluate
→ still low quality?
→ independent regeneration candidate_3
→ candidate selection
```

默认最大尝试：

```text
max_generation_attempts = 3
```

超过预算仍不理想：

- 保留当前最佳结果；
- 标记 Review Report；
- 不继续无限 regenerate。

## 6.3.5 Trigger 与 Selection/Stop 指标分离

Trigger Metrics 只回答：

> 第一次普通生成是否值得继续花额外算力？

可包括：

```text
technical_completeness
technical_coherence
task_relevance
specificity
generation_risk
```

Selection/Stop Metrics 回答：

> 新 candidate 是否更好、选哪个、什么时候停止？

至少考虑：

```text
absolute_quality
quality_delta
critical_issue
remaining_budget
```

具体阈值不能拍脑袋写死，必须由真实建设方案 eval 校准。

## 6.3.6 Evidence Gap 回退

如果 Generation Evaluator 明确判断失败根因是：

```text
evidence_gap
```

允许：

```text
Writer/Self-RAG
→ Supervisor
→ Research
→ Adaptive + C-RAG
→ Writer regenerate
```

如果只是 `generation_quality`，不得重新检索。

V2 对跨阶段回退设置硬预算，避免：

```text
Research ↔ Writer ↔ Research ↔ Writer ...
```

# 6.4 VerifierAgent

Verifier 负责语义级审查，不负责直接修改正文。

V2 保留三层验证概念：

```text
Paragraph Precheck
Section Verify
Document Verify
```

最终正式发布由 deterministic Hard Gate 决定。

## 6.4.1 Paragraph Precheck

优先使用确定性规则检查：

- 数量；
- 型号；
- 金额；
- 项目名称；
- Excel 中不存在的设备；
- FactSnapshot 明确冲突；
- Citation / Evidence ID 是否存在。

能用 deterministic rule 判断的，不调用大模型。

## 6.4.2 Section Verify

语义检查：

- Planner 要求是否覆盖；
- Fact/Evidence Binding；
- 证据支持是否充分；
- 内部技术逻辑；
- `suggested_design` 是否冒充事实；
- Claim 与正文是否一致；
- 是否存在旧项目污染。

输出：

```text
passed
repairable
need_more_evidence
review_required
```

Verifier 不直接调用 Writer / Research；它只返回问题类型和目标，由 Supervisor 路由。

## 6.4.3 Document Verify

所有 Section 完成后检查：

- 跨章节数量；
- 建设范围；
- 术语；
- 目标与技术方案关系；
- 重复或矛盾结论；
- 跨章节 Verified Claim 一致性。

只做局部 repair，不因为一个冲突重跑整篇方案。

## 6.4.4 Human Review 边界

Human Review 不再是正常运行中的 durable interrupt。

产品正常行为：

```text
一次输入
→ 直接生成完整方案
→ 同时生成 Review Report / 风险标记
→ 用户最后统一人工审阅
```

只有系统级 fatal error 才中止运行。

# 7. Memory + Context Engineering

这是 V2 Multi-Agent 的第一技术重点。

# 7.1 核心原则

```text
Agent 无状态
Memory 外置
Context 按需编译
History 不等于 Context
```

Agent 实例不能保存：

- 当前 Run 进度；
- Research 历史；
- Draft 历史；
- Verifier Issue；
- 跨调用聊天 history。

每次调用都由外部 Runtime 重新构造必要 Context。

## 7.2 短期记忆 Working Memory

由现有 GraphState / SectionState / LangGraph Checkpoint 承担。

典型内容：

```text
current section
current attempt
current research round
current paragraph cursor
current evidence package
current unresolved issue
current budget
```

作用是：

> 当前这一步正在做什么？

## 7.3 Run 级持久记忆 Durable Run Memory

V2 所谓“长期记忆”首先指：

> 在一个长 Run 中跨 Agent Invocation、跨 Section、跨故障恢复持续存在的结构化记忆。

不是用户人格记忆，也不是跨数月项目历史的自动复用系统。

核心记忆主题控制在：

```text
Fact
Evidence
Verified Claim
Research History
Writer Progress
Verifier Issue
Decision
Artifact Reference
```

不再建立过度庞大的记忆分类学作为实现目标。

## 7.4 最小 MemoryRecord

```yaml
MemoryRecord:
  memory_id: string
  run_id: string
  section_id: string | null
  paragraph_id: string | null
  attempt_id: string | null

  subject_type:
    - fact
    - evidence
    - verified_claim
    - research_history
    - writer_progress
    - verifier_issue
    - decision
    - artifact_ref

  content_ref: string | null
  structured_value: any | null
  source_refs: []
  authority_level: string
  relevance_keys: []

  lifecycle:
    - active
    - repaired      # verifier_issue only
    - resolved
    - superseded
    - invalid

  token_estimate: int | null
  created_at: datetime
  supersedes: []
```

原则：

- Memory 不成为第二事实源；
- Memory 必须能够回到 Event / Fact / Artifact / Claim；
- 不存模型私有 chain-of-thought；
- 不为了 Schema 完整性增加当前业务不用的 tenant/domain/version 层级。

## 7.5 Memory 写入：Event-driven Projection

模型不能直接写“长期记忆”。

只有已提交业务事件可以产生 Memory：

```text
ResearchRoundCommitted
EvidencePackageCommitted
ParagraphCommitted
ClaimVerified
VerifierIssueCreated
VerifierIssueRepaired
VerifierIssueResolved
SectionAccepted
DecisionCommitted
```

流程：

```text
Business operation commit
→ Domain Event
→ MemoryProjection
→ MemoryRecord
```

这样可以保证：

- 未提交 Token 不进入记忆；
- stale Attempt 不污染 active memory；
- LLM 不能随意篡改事实；
- event_id 可以作为幂等投影依据。

## 7.6 Memory 生命周期

V2 只处理同一 Run 内真正需要的生命周期，不建设 TTL / expiration 体系。

通用投影按需使用：

```text
active
resolved
superseded
invalid
```

`verifier_issue` 单独冻结为：

```text
active
→ Writer repair committed
→ repaired
→ Verifier confirms
→ resolved
```

```text
paragraph p003 v1
→ repair
→ p003 v2 active
→ p003 v1 superseded
```

```text
attempt-1 delayed result
→ attempt-2 already active
→ attempt-1 result invalid for active state
→ only Trace remains
```

不再实现 Excel 改动后跨 Run 的全局 MemoryInvalidator / Major Version reuse 图。

# 8. Context Compiler 与 Context Compression

这是 V2 Multi-Agent 的第二技术重点，也是 Memory 真正产生价值的地方。

## 8.1 唯一上下文入口

Agent 不直接访问 MemoryStore。

```text
AgentInvocationRequest
→ Role Policy
→ Memory Retrieval
→ Authority / Lifecycle Filter
→ Relevance Selection
→ Context Compression
→ Token Budget Check
→ AgentMemoryPackage
→ LLM
```

## 8.2 角色化 Context

Planner 主要需要：

- Template；
- FactSnapshot；
- SourceInventory；
- 必要的 Plan Decision。

Research 主要需要：

- Evidence Requirements；
- 当前 Fact subset；
- Query History；
- Accepted / Rejected Evidence；
- no-gain history；
- 当前 Evidence Gap。

Writer 主要需要：

- SectionPlan；
- Fact subset；
- EvidencePackage；
- 当前 Section 已提交 Paragraph 的压缩表示；
- 当前 unresolved Issue；
- 授权的跨章节 Verified Claim。

Writer 禁止默认读取：

- 其他 Section raw draft；
- 全部 Research reasoning；
- 全部 Tool raw result；
- resolved old issues。

Verifier 主要需要：

- 当前 Paragraph / Section；
- Fact / Evidence Binding；
- active Claim；
- unresolved Issue；
- DraftDiff；
- 必要跨章节 Verified Claim。

## 8.3 四级压缩策略

### Level A：不可损失的结构化事实

不得摘要改写：

```text
fact_id
设备名称
型号
规格
数量
金额
公式结果
claim_id
evidence_id
status
```

例如：

```text
server_count = 16
```

不能被压缩成：

```text
项目配置了一批服务器
```

### Level B：结构化压缩

Evidence：

```text
800-token raw chunk
→ evidence_id
→ source_ref
→ supported_claim
→ support_span
→ quality
```

Verifier Issue：

```text
完整审查历史
→ issue_id
→ target
→ problem
→ expected_fix
→ status
```

Research History：

```text
多轮 raw trace
→ searched_topics
→ accepted_evidence
→ rejected_patterns
→ missing_topics
→ no_gain_queries
```

### Level C：受控摘要

对已完成 Section、旧 Attempt、较长历史生成受控 Summary。

Summary 必须保留关键 ID 和来源引用，不能变成失去 lineage 的纯自然语言。

### Level D：Reference-only

大 Artifact、完整旧 Draft、长 Tool Result 默认只放：

```text
artifact_ref
```

只有当前任务真正需要时才展开。

## 8.4 Context 选择优先级

默认优先级：

```text
Authoritative Fact
> Current Project Material
> Unresolved Issue
> Verified Claim
> Current Evidence
> Current Section Summary
> Relevant Decision
> Prior Attempt Summary
> Resolved History
> Raw Historical Process
```

最终选择综合：

```text
role
relevance
authority
verification status
recency
token cost
```

V2 不在架构阶段拍脑袋冻结一组固定权重；通过 Trace/Eval 后校准。

## 8.5 Context Budget

当候选内容超预算时：

```text
先丢低权威
先丢低相关
先丢 resolved
先丢旧 Attempt raw process
再做结构化压缩
最后才考虑摘要
```

禁止简单从尾部暴力 truncate。

## 8.6 Memory Context Trace

每次 Agent 调用至少记录：

```yaml
memory_context:
  invocation_id: string
  agent_role: string
  requested_types: []
  selected_memory_refs: []
  omitted_memory_refs: []
  rejection_reasons: {}
  max_tokens: int
  estimated_tokens: int
  compressed_items: int
  package_hash: string
```

必须能回答：

- 为什么这条 Memory 进入 Context？
- 为什么另一条没进入？
- 压缩前后减少多少 Token？
- 关键 Fact 有没有丢？
- Writer 是否读取了越权 Draft？

# 9. Checkpoint + Crash Recovery + Idempotency

这是 V2 Multi-Agent 的第三技术重点。

## 9.1 不新增第二套 Checkpoint

继续使用现有官方 LangGraph SQLite Checkpointer。

Checkpoint 负责快速恢复工作流位置；Memory/Artifact 负责恢复业务内容。

## 9.2 两个重点恢复原子

### Research Round

```text
round1 committed
round2 committed
round3 running
→ crash
→ resume from round3
```

已经完成的 round1/round2 不重新执行。

### Paragraph

```text
p001 committed
p002 committed
p003 running
→ crash
→ resume from p003
```

p001/p002 不重新生成。

## 9.3 幂等键

所有有副作用的提交都必须有稳定逻辑身份：

```text
run_id
section_id
attempt_id
operation_id / paragraph_id / research_round_id
```

形成稳定 `idempotency_key`。

同一个操作重放：

```text
第一次 → commit
第二次 → return existing commit
```

不能生成两份 active Paragraph 或重复 Evidence commit。

## 9.4 stale Attempt

如果旧 Attempt 晚到：

```text
attempt-1 result arrives
attempt-2 already active
```

结果只能进入 Trace，不允许覆盖：

- active GraphState；
- active Artifact；
- active Memory；
- active Claim。

## 9.5 局部恢复

普通失败只允许局部恢复：

```text
Research → Research next round
Writer → current Paragraph repair
Verifier → targeted repair
Document conflict → affected Section
```

不因为单个 Section 或 Paragraph 问题重跑整个 Run。

不保存模型私有 chain-of-thought，只保存可审计的结构化输入、输出、reason code 和 outcome。

## 10.1 Adaptive Router Trace

```text
selected_action
confidence
reason_code
retrieval_result

token_cost
```

## 10.2 Research Trace

必须回答：

- 为什么继续搜？
- 为什么停止？
- 哪个 Evidence Requirement 仍未覆盖？
- 哪一轮开始 no-gain？

## 10.3 Writer / Self-RAG Trace

```text

facts_used
evidence_used
initial_quality
self_rag_triggered
trigger_reason

candidate_scores
selected_candidate
final_status
```

## 10.4 Verifier Trace

```text

target
severity
recommended_action
resolved
```

## 10.5 Memory / Context Trace

记录：

- selected memory；
- omitted memory；
- compaction；
- token budget；
- package hash；
- critical fact retention。

## 10.6 V2 Evaluation Signals

本节只冻结 Multi-Agent / RAG Runtime 必须暴露的可观察信号。正式 Core Metric、Gold、Judge、Result、Report 的 authority 属于独立 Evaluation Foundation，避免形成第二套 Eval 体系。

RAG：

```text
routing accuracy / retrieval utility
evidence requirement coverage
no-gain retrieval rate
retrieval tool calls
```

Generation：

```text
fact hallucination rate
self-rag trigger rate
self-rag repair success rate
technical quality delta
```

```text

idempotency violation count
stale-result rejection correctness
context token reduction
critical-memory retention
unauthorized-context leakage
```

System：

```text
average tool calls / section
tokens / section
latency / section
Hard Gate pass rate
Verifier repair rate
```

后续微调数据必须从稳定 Trace + Outcome 生成，而不是把某个 Teacher LLM 的判断直接当 Ground Truth。

```text
  ↓
Tool Gateway

  ├─ schema validation

  ├─ retry
```

# 12. Multi-Agent Contract + Section DAG

## 12.1 Agent 不自由聊天

四 Agent 只通过稳定强类型 Contract 协作：

```text
Planner
  ↓ SectionPlan
Research
  ↓ EvidencePackage
Writer
  ↓ DraftPackage / Paragraph Artifact
Verifier
  ↓ VerificationResult
```

核心 Contract 控制在少数几种：

```text
RunContext
SectionPlan
EvidencePackage
DraftPackage
ClaimRecord
VerificationResult
ReviewReport
```

禁止为了“强类型”不断扩展几十套平行 Schema。

## 12.2 DAG 只表达 Hard Dependency

```text
             ┌→ Compute ──┐
Planner ─────┼→ Network ───┼→ Document Verify
             └→ Security ──┘
```

无依赖 Section 并行。

只有确实需要前序 Verified Claim 时才建立依赖：

```text
Compute Verified Claim
      ↓
Network Section
```

“内容相关”不等于 Hard Dependency。

## 12.3 跨 Agent / 跨 Section 共享原则

```text
共享 Facts
共享 Evidence Package
共享 Verified Claim

按需可生成 Section Summary 作为 Context Projection，但它只能派生自现有 `artifact_ref` / `writer_progress`，不是第九种 Durable Memory，也不获得事实 Authority。

不共享所有 raw reasoning
不共享其他 Section 未验证 Draft
不共享全部 Tool Trace
```

核心原则：

> 共享经过治理的结果，不共享整锅思考过程。

# 13. Verification、Hard Gate 与最终交付

## 13.1 Claim

Writer 自报 Claim 只作为 Candidate / Hint。

关键 Claim 必须通过：

```text
Claim Extraction
→ Fact / Evidence Binding
→ Verifier
→ Verified / Rejected
```

`Verified Claim` 才允许成为跨章节 Memory。

## 13.2 Hard Gate

Document Verify 之后保留现有 deterministic Hard Gate。

Hard Gate 只检查明确 release 条件，例如：

- Required Section 是否存在；
- 关键项目事实是否覆盖；
- 是否仍有 fatal unresolved issue；
- 是否存在旧项目名或 placeholder；
- Citation / Evidence ID 是否有效；
- Document 状态是否一致；
- Review Report 是否生成。

LLM 不拥有最终 PASS authority。

## 13.3 Product 行为

正常用户体验：

```text
提交完整材料
→ 系统连续执行
→ 生成完整 Draft
→ 生成 Review Report
→ Hard Gate 判断能否作为正式 Artifact 发布
```

不在正常流程中频繁 Interrupt 用户。

Hard Gate PASS：

```text
Formal DOCX
```

Hard Gate FAIL：

```text
Rejected Draft
+
Review Report
```

V2 不把 `partial_success / failed skeleton DOCX / 多版本人工恢复` 作为新的重点开发目标；现有兼容行为可以保留，但不继续为此扩展复杂状态机。

# 17. V2 必须通过的核心验收场景

## MEM-01 Research History

第一轮已经执行某 Query；后续等价 Query 不产生无意义重复 Tool Call。

## MEM-02 Context Compression

历史超过 Token Budget 时：

- Fact 保留；
- unresolved Issue 保留；
- Verified Claim 保留；
- 当前 Evidence 保留；
- 旧 raw process 被压缩或只留 Ref；
- Trace 能看到 selected / omitted / compressed。

## MEM-03 Cross-section Verified Memory

计算资源章节已经验证：

```text
服务器数量 = 16
```

网络章节可以读取对应 Verified Claim，但不能读取计算资源未验证 raw draft。

## REC-01 Writer Crash Recovery

```text
p001 committed
p002 committed
p003 crash
```

恢复从 p003 开始，p001/p002 不重复生成。

## REC-02 Research Crash Recovery

已经提交的 Research Round 不重跑。

## REC-03 Stale Result

旧 Attempt 晚到不能写 active GraphState / Memory / Artifact。

## RAG-01 Adaptive Retrieval

同一 Eval Set 对比：

```text
Fixed / Heuristic Router
vs
3B Adaptive Router
```

至少输出：

- Evidence Coverage；
- Tool Calls；
- Latency；
- Cost；
- downstream quality。

## RAG-02 C-RAG Evidence Control

低质量 Evidence 能被识别并触发 targeted retrieval；达到 no-gain / budget 后能够正确停止。

## GEN-01 Self-RAG Fallback

普通技术段落生成质量足够时不触发额外计算；低质量时触发 critique rewrite；仍不足时最多再独立生成一个 candidate，随后停止。

## GEN-02 Evidence Gap Backtrack

只有明确 `evidence_gap` 才回 Research；普通 generation_quality 不允许回检索。

## VER-01 Fact Hallucination

历史方案 6 台，当前 FactSnapshot 16 台，最终 accepted 正文只能使用 16 台。

## OUT-01 Minimal DOCX

最终生成可打开的结构化文本 DOCX；不要求自动生成投资表、图纸或复杂排版。

# 18. 面试技术主轴

完成 V2 后，Multi-Agent 不以“Agent 数量”作为卖点。

统一陈述应接近：

> 我把建设方案场景限制在四个无状态业务 Agent：Planner、Research、Writer、Verifier。LLM 负责规划、检索策略、生成和语义验证，LangGraph 和确定性 Service 负责状态、DAG、预算、Retry、Checkpoint、幂等和最终发布。Agent 的长期运行记忆不放实例 history，而是由已提交 Event 投影成结构化 Run Memory；每次调用前由 ContextCompiler 按 Role、Relevance、Authority、Verification Status 和 Token Budget 选择并分层压缩上下文。Research 使用 Adaptive-RAG 的自适应检索思想和 C-RAG 的 Evidence Correction 思想；技术生成默认单次完成，只有质量不足时才进入 Self-RAG-like reflection fallback。所有关键决策写入 Trace，通过 Evidence Coverage、Context Compression、Recovery Correctness、Hallucination、Tool Cost 和 Latency 做 Eval。

重点必须有真实 Trace 和 Benchmark 支撑，而不是只背架构名词。

# 19. Definition of Done

V2 只有满足以下条件才算完成。

## 架构

- 唯一 Supervisor；
- 唯一生产顶层 Graph；
- 唯一 Section Graph；
- 四个业务 Agent；
- 不出现第二套 Runtime / State / Checkpoint / Router 主控制面。

## 输入与输出

- Agent 不直接读原始 Excel；
- ExcelParser → FactSnapshot 可追溯；
- 一个完整输入对应一个独立 Run；
- 输出是真实可打开的文本型 DOCX；
- 不自动生成投资估算表。

## RAG

- Adaptive Router 有真实策略 Trace；
- C-RAG-like Evidence Evaluator 有 coverage / conflict / no-gain；
- Self-RAG-like 只在技术生成低质量时触发；
- 所有循环有硬预算。

## Memory / Context

- Agent 跨调用无状态；
- Memory Event-driven；
- ContextCompiler 是唯一 Memory 入口；
- 关键 Fact 不因压缩丢失；
- 越权 Memory 不进入 Context；
- Memory Context Trace 可审计。

## Recovery

- Research Round 可恢复；
- Paragraph 可恢复；
- 幂等重放不重复提交；
- stale Attempt 被拒绝。

## Eval

- RAG、Generation、Memory、Recovery 都有真实指标；
- 至少完成一组 baseline vs improved A/B；
- Trace 可以形成后续 Router / Evaluator / Writer 的训练数据。

## 发布

- Document Verify 完成；
- Hard Gate 保持 deterministic final authority；
- PASS 才进入正式 Artifact；
- FAIL 输出 Rejected Draft + Review Report；
- Human Review 不作为正常运行中的中断节点。

# 20. 最终冻结原则

1. 功能做窄，技术做深。
2. 当前只做建设方案正文型 DOCX。
3. Excel 只解析，不由 Agent 修改或重新计算。
4. 投资估算表由人工粘贴，不自动生成。
5. 只保留 Planner / Research / Writer / Verifier 四个业务 Agent。
6. Agent 做非确定性认知工作，Service / Graph 做确定性工程工作。
7. RAG 技术深度放在 Adaptive Routing、Evidence Correction、技术生成 Reflection Fallback。
8. Agent Runtime 技术深度放在 Memory、Context Compiler、Compression、Recovery、Idempotency、Trace/Eval。
9. Agent 无状态，Memory 外置且由已提交事件产生。
10. Context 不是全部 History；按角色、相关性、权威性、验证状态和 Token Budget 动态编译。
11. 只传播 Verified Claim，不传播未验证 Draft。
12. 每个新完整输入创建新 Run，不做复杂跨 Run stale propagation。
