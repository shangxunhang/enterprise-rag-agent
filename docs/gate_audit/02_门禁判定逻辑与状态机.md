## 1. 范围、方法与判定口径

本阶段不重新盘点门禁，也不新增编号。所有结论均回填到 Phase 1 的 G01–G50：先定位独立判定点，再沿实际调用链核对输入、条件优先级、输出字段、状态传播、回退路径与聚合公式。

统一口径如下：

- **ROOT-CAPABLE / 独立控制**：具有独立判定或事实边界；是否真的产生新的业务失败事实仍按每个控制分别回答 YES/NO。
- **DERIVED**：只把已有事实投影为另一状态或布尔值；统一标注 `DERIVED — no new business judgement`。
- **AGGREGATED**：只汇总或重算既有事实；统一标注 `AGGREGATED — no new root failure fact`。
- **根失败**：`YES` 表示本控制能首次产生失败事实；`NO` 表示本控制不首次创建该业务失败事实，但仍可独立执行路由、构造、规范化、携带、聚合或投影。
- **Independent Decision ≠ Root Failure**：Independent Decision 表示组件拥有自己的条件判断和路由/状态决策；Root Failure 表示组件首次产生一个此前不存在的业务失败事实。因此一个 Control 可以是 Independent Decision，同时 Root Failure=`NO`。
- **模型调用影响**：`YES` 表示直接允许、阻止、触发或本身执行模型调用；`INDIRECT` 表示只通过后续路由影响；`NO` 表示发生在模型调用之后且不再触发模型路径。
- **Section 状态影响**：`DIRECT` 表示本控制直接写 Section 状态/检查；`DERIVED` 表示经后续控制投影；`NO` 表示不进入 Section 状态。
- **Formal Eligibility 影响**：`DIRECT` 表示进入 G25/G39 的正式资格公式；`DERIVED` 表示只经上游事实传播；`NO` 表示不参与。
- **Hard Gate 影响**：`DIRECT` 表示作为 G40/G41 的显式输入或检查；`PROPAGATED` 表示通过 Section、Formal、Evidence 等事实进入；`NO` 表示不进入文档硬门禁。
- **Human Review（HR）语义**分为：`PRODUCE`（产生复核事实）、`CARRY`（携带）、`AGGREGATE`（汇总）、`CONSUME`（阻断/放行时消费）、`INTERRUPT`（真实暂停工作流等待人工输入）。只有 G43 被证明执行 `INTERRUPT`。

“根失败”与“最终失败”不是同一概念。例如 G15 能产生新的 claim violation；G24 只把该事实投影到 Section；G39/G40 再聚合为 Formal/Document Hard Gate。后两者不因此成为新的根事实。

### 3.1 G01 EvidenceAssessor

- **代码 / class / method / line**：`backend/rag/plugins/evidence_assessors/plugin.py` / `CRAGEvidenceAssessorPlugin.assess()` / `74-139`（阈值初始化 `23-24`）；后端回退在 `backend/rag/judge/crag_judge.py`。
- **调用位置**：RAG 检索结果质量评估阶段。
- **实际输入**：检索条目、后端返回的 `retrieval_confidence`、相关性标签、`confidence_threshold`（默认 `0.55`）、`min_relevant_items`（默认 `1`）。初始化会把阈值夹到 `[0,1]`，最小相关数夹到非负整数。
- **精确条件与优先级**：先执行 LLM/确定性后端；再统计标签为 `relevant` 的条目数。`confidence < threshold` 追加低置信原因；`relevant_count < min_relevant_items` 追加相关条目不足原因；`sufficient = reasons 为空`。两个条件可同时失败，不短路。
- **输出/关联字段**：`sufficient`、`confidence`、`relevant_count`、`reasons`、`verification_mode`、`quality_mode_degraded`、后端 `metadata`。
- **模式**：正常 LLM 且无回退=`llm_verified`；配置不使用 LLM 的确定性路径=`deterministic_primary`；LLM 失败后确定性回退=`degraded_deterministic_fallback`；其他不可识别方法=`unavailable`。预算超限/取消异常不在后端吞掉；普通 LLM 异常是否回退取决于回退配置。
- **根失败**：`YES`；最小条件为低置信或相关条目数不足任一成立。
- **影响**：模型调用=`YES`（评估器可调用质量模型）；Section=`DERIVED`；Formal=`DERIVED`；Hard Gate=`PROPAGATED`；HR=`NO`（本控制不直接产生 HR）。

### 3.2 G02 CorrectionGate

- **代码 / class / method / line**：`backend/rag/plugins/correction_gates/plugin.py` / `EvidenceSufficiencyCorrectionGate.decide()` / `16-44`。
- **实际输入**：G01 `assessment.sufficient`、`budget`、`completed_rounds`。
- **精确条件与优先级**：`budget=max(0,budget)`；`completed=max(0,completed)`；`remaining=max(0,budget-completed)`；`required = (not sufficient) and remaining>0`。原因优先级为：证据充分 → 预算耗尽 → 使用 G01 原因。
- **输出/关联字段**：`required`、`remaining_rounds`、`reason`。
- **Independent Decision**：`YES`；这是 Corrective Retrieval Route Decision，根据 G01 已产生的 evidence sufficiency 与 correction budget 决定是否继续纠正检索。
- **根失败**：`NO`；`assessment.sufficient=false` 且 `remaining=0` 只表示纠正检索路径已耗尽、不再继续 correction。原始 evidence insufficient 事实来自 G01；最终是否允许生成仍由最终证据重新进入 G04→G05→G06 后决定。G02 不直接产生 Evidence BLOCKED、Section FAILED、Formal false 或 Hard Gate false。
- **影响**：模型调用=`INDIRECT`（触发额外检索/评估路径）；Section=`DERIVED`；Formal=`DERIVED`；Hard Gate=`PROPAGATED`；HR=`NO`。

### 3.4 G04 单条证据资格与事实状态策略

- **代码 / function / line**：`backend/rag/evidence/governance_v2.py` / `resolve_fact_claim_eligibility()`, `_item_assessment()` / `277-379,438-574`。
- **实际输入**：每条 evidence item 的主题、语义分、CRAG label、允许/禁止 claim、项目关系、事实状态、来源权威级、来源形态、章节结构兼容性。
- **主题/相关性优先级**：topic overlap `>=0.30` 才计支持该 topic；任一 topic `>=0.60` 或 semantic `>=0.70` 为 relevant；任一 topic 或 semantic `>=0.25` 为 partial；否则 irrelevant。若 CRAG 最终标签为 irrelevant，则覆盖前述结果为 irrelevant，并清空支持 topics。
- **claim 集合处理顺序**：先 `allowed - forbidden`；再移除错误项目关系下的当前项目 claim；再移除与章节结构不兼容的 claim；最后套用事实状态策略。`eligibility = bool(supported_claims) and relevance != IRRELEVANT`。
- **事实状态策略优先级**：
  1. 非当前项目 claim：`eligible=true, not_applicable`；
  2. 项目关系错误：不合格并要求 HR；
  3. `UNKNOWN`：不合格，限定词“尚未确认”，要求 HR；
  4. `ESTIMATED`：只允许 estimate 类型，附限定词，要求 HR；
  5. `PROPOSED`：允许但附“拟/尚待确认”，要求 HR；
  6. `PLANNED`：允许但附计划限定词，要求 HR；
  7. `CONFIRMED`：仅 authoritative/official/confirmed 来源合格；
  8. `DECIDED`：除权威来源外，source form 还必须包含 decision/approval/procurement_result/tender_result/contract/meeting_minutes/official_notice 或对应中文标记，否则不合格并要求 HR。
- **输出/关联字段**：单条 `eligible`、`relevance`、`supported_topics`、`supported_claims`、`forbidden_claims`、status qualifiers、`metadata.human_review_required`、原因。
- **根失败**：`YES`；最小条件为 item irrelevant、无可支持 claim、项目关系错误、结构不兼容或事实状态策略拒绝任一成立。
- **影响**：模型调用=`NO`（消费已给定分数/标签）；Section=`DERIVED`；Formal=`DERIVED`；Hard Gate=`PROPAGATED`；HR=`PRODUCE`。

### 3.5 G05 EvidenceAssessment

`AGGREGATED — no new root failure fact`

- **代码**：`backend/rag/evidence/governance_v2.py:673-741`。
- **公式**：
  - `eligible_items = {i | G04(i).eligible}`；
  - `covered_topics = required_topics ∩ ⋃ eligible_item.supported_topics`；
  - `missing_topics = required_topics - covered_topics`；
  - `coverage_ratio = |covered_topics| / |required_topics|`（无覆盖/无 eligible 时显式为 `0`；全覆盖时为 `1`）；
  - `supporting_items = eligible_items`，但 ABSENT 分支清空。
- **状态优先级**：`conflicts 非空 → CONFLICTED`；否则 `eligible_items 为空 or covered_topics 为空 → ABSENT`；否则 `missing_topics 为空 → SUFFICIENT`；否则 `PARTIAL`。
- **输出**：`status`、`coverage_ratio`、`covered_topics`、`missing_topics`、`supporting_items`、`conflicts`。
- **影响**：根失败=`NO`；模型调用=`NO`；Section=`DERIVED`；Formal=`DERIVED`；Hard Gate=`PROPAGATED`；HR=`AGGREGATE`（冲突事实由上游产生）。

### 3.6 G06 GateDecision

- **代码 / function / line**：`backend/rag/evidence/governance_v2.py` / `_gate()` / `755-904`；`EvidenceGovernanceV2Result.to_dict()` 的 `generation_allowed` 投影在 `142-147`。
- **实际输入**：G03 requirements、G05 assessment、合格条目的 claim/来源/事实状态元数据、Prompt 来源、claim risk。
- **预计算**：`allowed_claims=合格条目 supported_claims 并集`；`forbidden_claims=所有条目 forbidden 并集 - allowed_claims`。风险：当前项目 claim 或采购类→HIGH；政策/技术类→MEDIUM；其他→LOW。另聚合 authoritative、historical/reference、status qualifiers、HR 标记。
- **精确 if/elif 优先级**：
  1. `prompt_missing` → `BLOCKED`，`allowed_claims=[]`；
  2. assessment `CONFLICTED` → `HUMAN_REVIEW`，`allowed_claims=[]`，HR=true；
  3. assessment `SUFFICIENT`：有事实状态限定词→`QUALIFIED`；否则 allowed 仅为模板类→`GROUNDED`；否则含当前项目 claim 且无权威来源→`QUALIFIED`，高/关键风险时 HR=true；否则 historical/reference→`QUALIFIED`；否则 `GROUNDED`；
  4. assessment `PARTIAL`：高/关键风险→`HUMAN_REVIEW` 且 allowed 清空；否则 `QUALIFIED` 并加入缺口/谨慎限定词，HR=true；
  5. 其余（ABSENT/NOT_ASSESSED）→`BLOCKED` 且 allowed 清空。
- **后置覆盖**：若 `prompt_source=legacy_fallback` 且初始模式属于 GROUNDED/QUALIFIED/FRAMEWORK_ONLY，则强制为 `QUALIFIED`、追加限定词并 HR=true。
- **输出/关联字段**：`mode`、`allowed_claim_types`、`forbidden_claim_types`、`qualifiers`、`covered/missing_topics`、`risk_level`、`human_review_required`、原因、lineage；`generation_allowed = mode in {GROUNDED, QUALIFIED, FRAMEWORK_ONLY}`。
- **Observed behavior**：Schema 存在 `FRAMEWORK_ONLY`，但当前 `_gate` 分支没有赋出该模式。
- **根失败**：`YES`；最小条件为 prompt 缺失、证据冲突、证据 ABSENT/NOT_ASSESSED，或 PARTIAL 且风险为 HIGH/CRITICAL。
- **影响**：模型调用=`YES`（经 G10/G11 直接决定 writer 是否可调用）；Section=`DERIVED`；Formal=`DIRECT`；Hard Gate=`PROPAGATED`；HR=`PRODUCE/CARRY`。

### 3.7 G07 GateDecision Schema 不变量

- **代码 / class / method / line**：`backend/apps/enterprise_document/schemas/gate_decision.py` / `GateDecisionSchema._decision_is_consistent()` / `57-149`。

## 8. Formal Eligibility：G25 → G39 → G40 → G47 → G48

### 8.1 三个不同的 Formal 层次

1. **G25 upstream formal eligibility**：章节生成当时的投影值。
2. **G39 recomputed formal eligibility**：在最终持久化 Section artifact 上重新验证的正式资格。
3. **G47 release proof eligibility**：要求所有章节的 G39 重算结果均真并且无 HR，形成发布证明。

三者不能互换。G39 还专门比较 G25 与重算值是否一致。

### 8.2 G39 Writer Formal Eligibility Recompute

`AGGREGATED — no new root failure fact`

- **代码**：`backend/apps/enterprise_document/services/writer_artifact_integrity.py:258-655`。
- **实际输入**：最终 Section artifact、G10 binding、G15 audit、正文、identity/lineage/hash、Section status、G25 上游 formal bool。
- **前置失败**：binding 缺失或无效时直接返回所有检查 false。

- **代码 / class / method / line**：`backend/apps/enterprise_document/workflows/top_level_business_graph.py` / `EnterpriseDocumentWorkflowEngine._run_stage()`, `_failure_payload()` / `850-1079`，以及 `backend/apps/enterprise_document/services/scheme_writer/stage_service.py` / `finalize_workflow_failure()`, `mark_technical_failure()` / `2188-2321`。
- **实际输入**：节点异常、timeout/cancel、模型/RAG预算异常、外部提交状态、写契约、返回 payload 类型、重试配置。
- **精确条件/优先级**：先验证节点返回 payload 类型与 write contract；runner 最多 `max_retries+1` 次；只有仍有 attempts、错误 retryable、未 cancelled、worker 不 active 才重试。timeout、cancel、无结果、external commit、write-contract、stage exception 被分类；重试耗尽或错误 payload 路由 technical_failure。
- **输出**：status=`RETRYABLE_FAILED` 或 `FAILED`、technical error、rejected/technical artifact、`requires_human_review=true`。
- **根失败**：`YES`；最小条件为任何未被业务状态吸收的技术异常，且不满足继续重试条件或重试耗尽。
- **影响**：模型调用=`YES`（控制是否重试模型/RAG节点）；Section=`NO/旁路`；Formal=`NO/无法形成或作废`；Hard Gate=`NO/旁路`；HR=`PRODUCE`。

### 10.3 G50 Top-Level Need-Review Projection

`DERIVED — no new business judgement`

- **代码**：`backend/apps/enterprise_document/services/scheme_writer/stage_service.py:1817-1864,2200-2321` 的持久化输出/result projection。
- **公式**：正常持久化输出 `need_review = (deliverable_final_result is None)`；顶层 Result 继承该值；technical failure 始终 true。
- **影响**：根失败=`NO`；模型调用=`NO`；Section=`NO`；Formal=`NO`；Hard Gate=`DERIVED`；HR=`CARRY`。

### 10.4 顶层状态流

```text
G42 deliverable → G46 output invariant → G47 proof → G48 publish → persist
G42 rejected    → G46 output invariant                         → persist rejected
any technical/schema/write failure → G49 technical_failure    → persist failure
```

业务拒绝、人工拒绝、技术失败具有不同来源：业务拒绝保留 G40/G41 failure；人工拒绝由 G44 产生；技术失败由 G49 产生。三者最终都可能没有 deliverable，从而经 G50 投影 `need_review=true`，但不能据此反推它们是同一失败类型。

### 11.3 Section、Formal、Hard Gate 的不可逆传播边界

- Section `PARTIAL` 不等于 Formal false：G25/G39 允许状态为 SUCCESS 或 PARTIAL，但仍要求 audit/binding/HR/lineage 全部成立。
- Section `FAILED` 会使 G25/G39 false，并经 G40 的 Section status/formal 检查进入 hard failure。
- GateDecision `HUMAN_REVIEW` 在 G11 发生于 writer 模型前；claim audit HR 在 writer 模型后由 G24/G25/G39 消费。
- G40/G41 false 经 G42 只能投影 rejected；G44 approve 不覆盖该结果。
- G47/G48 只消费已通过的 hard/formal 事实；它们不把失败修正为通过。

## 13. Phase 1 与 Phase 2 的明确差异/精化

本阶段未发现需要重编号、拆分或新增 G 控制的证据；G01–G50 沿用不变。以下是基于分支级取证对 Phase 1 总表的明确精化，不是新控制：

1. **G39 的“21 项”精确定义**：重算 formal eligibility 使用前 20 项；第 21 项单独比较 G25 上游 formal bool 与重算 bool。因而“21 项全真”和“recomputed formal=true”不是同一布尔量。
2. **G35 的状态可达性**：当前 resolver 可达 `OBSOLETE`、`FAILED`、`BLOCKED`，未发现写出 `RESOLVED` 的分支；G41 却只把 RESOLVED/OBSOLETE 视为闭合。
3. **G45 的 WAITING_HUMAN 可达条件**：hard gate projection 的优先级高于 waiting-human projection；正常 G43 显式审批路径已有 hard gate，所以 document validation 通常保留 PASSED/FAILED。
4. **G32 的聚合范围**：其公式只 OR 预算耗尽策略、gate HR、binding 缺失、claim audit failed；不是对所有 `section.extra.need_review` 的通用聚合。
5. **G08 的性质确认**：ContextGate 没有 PASS/FAIL 状态，不能按名字推断为质量门禁。
6. **G21 的 hard issue 落点**：semantic judge 内部可以产生 fail/hard issue，但 SectionQualityEvaluator 当前统一映射到 warning；直接 Section 状态为 PARTIAL，而非由 G21 单独置 FAILED。
7. **G43 的真实中断边界**：项目中多处产生 HR/need-review 数据，但在本主链取证中只有 G43 调用真实 interrupt。
8. **G13 的 root-failure 精化**：它对 substantive set 独立判定，属于 Phase 1 的 ROOT-CAPABLE detector，但代码明确不决定 PASS；新的 claim failure 由 G15 创建。
