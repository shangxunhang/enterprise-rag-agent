## 1. Phase 3 范围与术语

本阶段不再回答 Control 有哪些、条件如何判定，只回答一个失败事实从首次出现到最终 artifact route 的字段传播。计数单位是 **独立 Root Event**，不是 violation 行数、false check 数、failure message 数或失败 Section 数。

统一类型只使用：

- `ROOT`：当前链路中首次产生此前不存在的业务失败事实。
- `DERIVED`：机械读取、组合或投影已有 Root，不产生新业务失败。
- `AGGREGATED`：汇总多个 Root/Derived 形成集合或文档级结果。
- `INDEPENDENT_PARALLEL`：与当前分析链同时存在、但即使当前 Root 不存在也能独立失败的另一项检查；它在自己的链上仍是独立 Root Event。
- `TECHNICAL`：Schema、contract、timeout、exception、模型/工具基础设施、持久化完整性等技术失败，不计入业务 Root。
- `N/A`：字段或路由不是 failure，例如 G02 的 correction route decision、G43 的审批请求开关。

`Independent Decision ≠ Root Failure`：组件可以拥有自己的条件判断与路由决策，但不首次创造业务失败。G02、G03 是明确例子。

本文使用两个层级：

1. **Root Family**：稳定的语义族，例如 `CLAIM_POLICY`。
2. **Root Event**：某次执行中具体的一条首次失败事实，例如某一 sentence 的 `claim_type_not_allowed`。同一 family 可有多个独立 event；同一 event 可投影出多个后续 failure。

## 2. Root / Derived / Aggregated 判定标准

### 2.1 首次写入测试

某字段为 false 不自动等于 Root。先向上追踪其直接输入：

- 若该 Control 首次创建 violation/conflict/issue/error，且上游没有同一业务失败事实，标 `ROOT`。
- 若该 Control 只执行 `passed = not violations`、`status = FAILED if upstream false`、`all(checks)` 或复制 failure code，标 `DERIVED`/`AGGREGATED`。
- 若异常、验证错误或持久化错误首次出现，标 `TECHNICAL`。

**Earliest-Failure Principle**：Root Event 必须落在当前传播链最早首次产生失败事实的位置，而不是最先看到 false 的位置。归因时依次检查：上游是否已有同一 failure、当前 Control 是否使用独立新输入、该 failure 在上游成功时是否仍可独立成立；下游仅转换 failure code/bool/status 时不得重复计 Root。

### 2.2 反事实独立性测试

- **Same Root / Derived**：令上游 A 成功后，B 不再可能因该原因失败；或 B 机械读取 A。
- **Independent Failure**：即使 A 完全成功，B 仍可凭自己的输入独立失败。

例如，`audit.passed=false → Section.status=FAILED → formal=false` 是同一 Claim Root 的传播；而 Claim Audit 全通过时，citation occurrence 仍可独立失败，所以 Citation 是 `INDEPENDENT_PARALLEL`。

### 2.3 一个 Control 可以有双重角色

- G05 `_conflicts()` 首次创建 `EvidenceConflictSchema` 时是 Root detector；同一 G05 把 items 汇总成 `EvidenceSetAssessment.status` 时是 AGGREGATED。
- G37 对 G36 failures 的原样返回是 DERIVED；G37 自己发现 Prompt leak、旧项目名、营销语言或相邻重复正文时是 ROOT。
- G40 对已有 Section/Writer/Citation 事实是 AGGREGATED；它不因重新计算多个 checks 而创造多个 Root。

### 2.4 计数边界

本文的 “downstream count” 只统计明确列出的 canonical 字段/状态，不把同一字段的日志文本、metadata 镜像或中文 failure message 再计一次。若一个 G40 check 同时产生一条 `failures[]` 文本，Root 计数仍不增加。

### 4.2 G02 边界

G02 的 `remaining=0` 不直接创建 Evidence BLOCKED、Section FAILED、formal false 或 Hard Gate false。它只结束 corrective retrieval 路由。若最终 evidence 在 G04/G05 变为 sufficient，G06 仍可放行；因此 `correction exhausted` 不计业务 Root。

### 4.3 G04 双重角色

G04 的 `eligibility=false` 不能脱离 `reason_codes` 与 metadata 直接计 Root：

- 若 `crag_final_judgement.relevance=irrelevant`，G04 强制 `relevance=IRRELEVANT`、清空 `supported_topics`，并写入 `rejected_by_final_crag_irrelevant`；最早 failure 是上游 CRAG relevance judgement，G04 只是 `DERIVED`。
- 若没有更早的同一 failure，G04 由 `current_project_claim_requires_current_project_relation`、`structured_evidence_incompatible:*`、`document_profile_has_no_eligible_claim_capability`、fact/authority/source-form policy，或本地 `semantic_relevance_below_threshold` 首次拒绝 evidence，则该具体 G04 rejection 是 `EVIDENCE_ELIGIBILITY` 的 `ROOT`。

因此不能用 `eligibility=false` 一个布尔值区分两者，必须先查看 `reason_codes`、`crag_final_judgement` 与 `governance_relevance_before_crag`。

### 4.4 Prompt missing 支线

G03 只把上游 context 的 `prompt_evidence_contract_missing` carry/normalize 到 requirements。G09 首次形成 strict prompt-visible contract 缺失事实；G06 首次把该事实转换为 `delivery_mode=BLOCKED`。本链计一个 `PROMPT_EVIDENCE_CONTRACT` Root，不把 G03 与 G06 再各计一次。

### 4.5 G11 诊断 Section 的传播特点

G11 的 evidence-insufficient 或 writer-gate-blocked artifact 是 `PARTIAL_SUCCESS`，不是 Section FAILED；但它携带：

- `generation_blocked=true`；
- `generation_allowed=false` / `claim_audit.passed=false`；
- `formal_deliverable_eligible=false`；
- 可选 `need_human_review=true`。

因此 G39/G40 可在 Section status 仍为 PARTIAL 时通过 writer generation/formal checks 拒绝文档。`Section.status=FAILED` 不是 evidence block 传播的必要中间状态。

## 5. Claim Audit Failure Propagation

### 5.1 G14/G15 首次 Root 边界

G13 只定义 substantive sentence set。对 semantic classification，必须先检查 G14 `SemanticClaimBatchResult.calls` 与 execution outcome，再解释 G15 violation：

- **Path A — Technical Classifier Failure**：`model_gateway is None`、`ModelResponse.success=false`、调用异常、`parse_error`、非法 `items` contract、sentence id 缺失，或 retry 后仍有 `missing_sentence_ids`。最早 failure 是 G14 的 `TECHNICAL` event；随后 G15 因 classification 缺失写入 `semantic_unclassified_substantive_claim`，只是 `DERIVED` fail-closed business manifestation。
- **Path B — Classification Quality Failure**：G14 调用成功，response/items/id contract 合法且 classification artifact 已形成，但合法结果为空 ClaimType、`confidence < 0.70`，或 deterministic classification 无法满足分类要求。G15 对应 `semantic_unclassified_substantive_claim`、`unclassified_substantive_claim` 或 `unclassified_or_low_confidence_claim` 是 `CLAIM_CLASSIFICATION` 业务 `ROOT`。
- **Policy/Qualifier**：`forbidden_claim_type_generated`、`claim_type_not_allowed` 与 `required_qualifier_missing` 仍由 G15 独立规则首次产生，分别是 `CLAIM_POLICY` / `QUALIFIER` 业务 `ROOT`。

同一 technical event 导致 classification missing 时，不得同时计 “1 个 G14 Technical Root + 1 个 G15 semantic_unclassified business Root”；只有存在另一个独立、技术成功后的分类质量事件时才能另计。后续 `audit.passed=false` 始终只是汇总状态。

### 5.3 一对多静态计数：孤立 `claim_type_not_allowed`

假设其他 Evidence、Citation、Assembly、Document checks 全部通过，且只有一条 `claim_type_not_allowed`：

- **Actual Root Event count：1**。
- **G40 false check / failure-message count：5**：`writer_human_review_clear`、`writer_claim_audits_passed`、`writer_section_status_deliverable`、`writer_formal_deliverable_eligible`、`section_status_valid`。
- **Canonical downstream field/status count：27**：按上节明确列出的 audit 3 项、Section eval/error/status 5 项、G25/G32 3 项、G39 4 项、G40 6 项、G41/G42/final 6 项计数；不含原始 violation、日志、metadata 镜像和中文 message。

这里 `writer_claim_audit_recomputed_valid` 仍可为 true，因为重算能复现同一个失败 audit；`writer_formal_eligibility_recomputed` 也可为 true，因为上游 formal=false 与重算 formal=false 一致。它们不是额外 failure。

### 5.4 重复报错边界

下列字段在孤立 Claim Root 下属于 **same root family / derived**，不能分别计根因：

`audit.passed=false`、Section FAILED、`formal_deliverable_eligible=false`、G39/G40 writer checks、HardGate false、rejected、最终 need review。

若同时存在 citation grounding failure，则 Citation failure 即使 Claim Audit 全通过仍能独立成立，必须另计一个 Root Event。

## 6. Citation / Grounding Failure Propagation

### 6.1 Citation availability / grounding 判断链

```text
citation_required?
  ├─ NO → 无 required-citation failure
  └─ YES
      ↓ citations available?
      ├─ NO: citations=[]
      │     ↓ 查上游 retrieval / evidence mapping /
      │       required-section citation availability
      │   G19 bindings=[]                                DERIVED: 无输入可绑定
      └─ YES: citations 非空
            ↓ G19 bind_citations + supported_bindings
          verified binding?
            ├─ YES → pass
            └─ NO: bindings=[]                           ROOT: CITATION grounding

任一 required citation 最终无 binding 的下游投影
  ├→ reconcile 删除未验证 marker                         DERIVED
  ├→ G23 citation_bound=false → Section FAILED           DERIVED
  └→ G38/G40 occurrence、required-section、target、
      grounding checks                                   AGGREGATED / same family
       → G40 passed=false → G42 rejected                 AGGREGATED / DERIVED
```

`bindings=[]` 本身不能确定 Root。`citations=[]` 时 G19 没有 citation evidence 可执行 grounding，必须继续向上追踪 availability；只有 `citations` 非空且 G19 实际执行 binding/support 校验后仍无 verified binding，才把该 rejection 计为 `CITATION` grounding Root。并非每个 G19 grounding failure 都必然使 G38 四项全部失败：reconcile 删除 marker 后，可能表现为 required citation section 无 binding，而不是 orphan marker。传播矩阵只列可能触发的 checks，不假定它们同时为 false。

### 6.2 High-risk fact 是独立检查

G22/G40 的 high-risk 支持要求包含 ledger 或精确 fact identity、marker 位置与 verified binding。普通 citation grounding 可以通过，而 high-risk 仍可因 unsupported/ambiguous 失败；反之亦然。因此 `HIGH_RISK_FACT` 与普通 `CITATION` 是两个独立 Root Family。

### 6.3 与 Claim Audit 的并行关系

Claim policy 判断 claim type 是否被 writer gate 允许；Citation 判断正文断言是否有绑定证据；High-risk gate 判断高风险项目事实的精确支撑。三者输入与失败条件不同，均可在其他两者成功时独立失败，汇聚到同一个 G40 不会把三者合并为一个 Root。

## 7. Section Status Failure Propagation

Section status 是多来源投影，不允许由 `FAILED` 反推单一 Root。

| 赋值点 | 触发来源 | 写入状态 | 类型 | 是否覆盖旧状态 / 顺序 | 后续读取者 |
|---|---|---|---|---|---|
| G11 `build_insufficient_evidence_section()` | Evidence 最终不足且无正式生成 | PARTIAL_SUCCESS | DERIVED | 创建诊断 Section；无旧状态 | G33、G39、G40 |
| G11 `build_gate_blocked_section()` | Gate BLOCKED/HUMAN_REVIEW、legacy incomplete | PARTIAL_SUCCESS | DERIVED | 创建诊断 Section；eval passed=false | G33、G39、G40 |
| G18 model failure return | response.success=false | FAILED 或 RETRYABLE_FAILED | ROOT | 首次 failure 与状态写入同点；立即返回，G23/G24 不执行 | G31、G34、G39、G40 |
| G23 content/truncation evaluator | content empty / truncated | FAILED | ROOT | 初始质量状态；发生在 G24 前 | G24、G28、G39、G40 |
| G23 citation-bound evaluator | citation unbound | FAILED | DERIVED | 投影上游 citation availability 或 G19 grounding failure；发生在 G24 前 | G24、G28、G39、G40 |
| G23 advisory aggregate | Self-RAG、semantic、长度、scope warning | PARTIAL_SUCCESS | AGGREGATED | 无 hard failure 时汇总为 PARTIAL；各 warning 的 Root 身份分别见 G20/G21 | G28、G39、G40/G42 |
| G23 no issue | hard checks 与 warnings 均空 | SUCCESS | N/A | 基础成功状态 | G24、G28、G39、G40 |
| G24 claim audit override | `claim_audit.passed=false` | FAILED | DERIVED | 无条件覆盖 G23 的 SUCCESS/PARTIAL/FAILED 为 FAILED | G28、G39、G40 |
| G27 paragraph snapshot | blocked paragraph 且剩余正文非空/为空 | PARTIAL_SUCCESS / FAILED | DERIVED | 覆盖当时 status；无 block 保留旧值 | G28、G31、G39、G40 |
| G31 budget projection | budget exhausted | PARTIAL_SUCCESS；已有 hard failure 时保持/强制 FAILED | DERIVED | 在 finalize 阶段执行；不把已有 hard failure 降为 PARTIAL | G39、G40、G42 |

覆盖顺序的静态主线是：G18 失败会早退；正常生成时 G23 → G24 → G27 → G31。G28 REJECT 自身只 finalize，不保证改写 status，因此不是可靠的 `Section.status=FAILED` 来源。

### 7.1 `Section.status=FAILED` 的可能 Root

- SECTION_MODEL：G18 模型调用失败。
- SECTION_QUALITY：正文空或截断。
- CITATION：上游 citation availability failure，或 citations 非空时的 G19 grounding failure，经 G23 投影。
- CLAIM_CLASSIFICATION / CLAIM_POLICY / QUALIFIER：G14 technical failure 经 G15 fail-closed，或 G15 独立业务 violation，经 G24 投影。
- PARAGRAPH_FACT：G26 经 G27，且删去 blocked paragraph 后正文为空。
- BUDGET：G30/G31；若预算事件与已有 hard failure 并存，二者是独立并行条件，不应把原 hard failure归因给预算。

`Section.status=FAILED` 只说明至少一条上述链到达状态投影，不包含唯一 root identity。

### 8.3 Claim HR 链


### 8.5 Workflow interrupt 链

只有 G43 在 `require_human_approval=true` 且尚无 decision 时调用 LangGraph `interrupt()`。它不消费 Gate/Claim/Section HR 字段，也不以 G41 passed 为前提。G44 approve 保留原 hard-gate route；reject/cancel 独立改写 output status/route。因而“风险状态 HR”与“审批 interrupt”是两条不同链。

### 9.1 来源树

```text
业务 Roots
├─ Evidence/Gate block or gate HR
├─ Claim violation / audit false
├─ Section status non-deliverable
├─ qualifier missing
└─ independent artifact/lineage/schema integrity failure
        ↓

        ↓
```

### 9.2 各层角色

| 层 | 字段 | 角色 | 是否新增业务 Root |
|---|---|---|---|
| G25 | Section extra `formal_deliverable_eligible` | 第一次、非 authoritative 投影 | NO |
| G39 | `recomputed_formal_deliverable_eligible` | 从最终 artifact 重算的 authoritative formal | NO；汇总已有业务/完整性事实 |
| G39 | `writer_formal_eligibility_recomputed` | 比较 G25 与 G39；不比较业务内容本身 | NO；不一致是 TECHNICAL artifact consistency |
| G40 | `writer_formal_deliverable_eligible` | 所有 Section formal 的文档级聚合 | NO |

| G48 | manifest/document/proof verify | 写前、写后、回读完整性 | NO；异常是 TECHNICAL |

### 9.3 同一 Root 的 Formal 重复表现

孤立的 `claim_type_not_allowed` 在主线至少表现为三处 formal false：

1. G25 upstream `formal_deliverable_eligible=false`；
2. G39 `recomputed_formal_deliverable_eligible=false`；
3. G40 `writer_formal_deliverable_eligible=false`。

G39 的 consistency check 在这条正常传播中为 true，因为 false 与 false 一致；G47 因 G42 已选择 rejected 不会在正常路由被调用。因此三处 formal false 仍只对应一个 Claim Root。

如果 G25 被错误记录为 true、而 G39 重算为 false，则 `writer_formal_eligibility_recomputed=false` 是额外的 TECHNICAL consistency failure；它与原业务 Claim Root 并存，不能合并。

## 11. Release / Technical Failure Propagation

### 11.1 业务拒绝路径

`G40/G41 passed=false → G42 rejected → persist_rejected()` 创建 `RejectedDraftArtifactSchema(rejection_code=DOCUMENT_HARD_GATE_FAILED)`；G48 不执行。这里 rejected 是业务 Root 的 DERIVED 生命周期结果。

### 11.2 人工拒绝路径

G44 reviewer reject 首次创建 `HUMAN_REVIEW_REJECTED`，并把 route 改为 rejected。它不修改 hard gate，因此是独立 `HUMAN_APPROVAL` Root，而不是 G40 failure 的投影。approve 不是 failure，cancel 是独立 workflow cancellation state。

### 11.3 发布路径

G47 只在 hard gate 已通过、output status 可发布、Stage-E writer/formal checks 全真时构建 proof。它重跑 G39并固化 Section/binding/audit hashes；这些是发布 precondition，不是新的业务 Root。

G48 的同 identity/同 request 返回 idempotent replay；同 identity/不同 request、proof/hash 变化、artifact/manifest 完整性或写后验证失败属于 TECHNICAL `RELEASE` event，并进入 G49。

### 11.4 技术失败链

G14 classifier technical event 是本节的 fail-closed 特例：call/parse/items/id/retry failure 被保存在 `SemanticClaimBatchResult.calls`，缺失 classification 由 G15 转成 `semantic_unclassified_substantive_claim`，再沿 Claim → Section → Formal → Hard Gate 传播；该技术 Root 不必抛异常进入 G49，也不得再增加一个业务 classification Root。

```text
G07 GateDecision ValidationError
或 G09 strict contract exception
或 G10 binding/schema exception
或 G16 ClaimAudit ValidationError
或 G46 output lifecycle ValidationError
或 G48 release conflict/verification/persistence exception
或 timeout / no result / write-contract / external commit / model infra
        ↓
top_level_business_graph error mapping
        ↓
仍有 attempt ∧ retryable ∧ 未取消 ∧ worker 非 active ? retry : stop
        ↓
G49 technical_failure route
        ↓
finalize_workflow_failure
        ↓
status=FAILED/RETRYABLE_FAILED
artifact_route=technical_failure
deliverable=None, rejected_artifact=None
AgentResult.need_human_review=true
```

技术失败不进入业务 Root Family 计数；它有独立 Technical Event count。G46/G48 发生在 Hard Gate 之后也不会回写一个假的 `HardGateResult.passed=false`。

## 16. Same Root vs Independent Failure 判定

### 16.1 Same Root Family / Derived

满足任一条件：

1. B 直接读取 A 的 bool/list/status；
2. 在其他输入固定成功时，A 恢复为成功会使 B 必然恢复；
3. B 只是 `all/any/not`、status mapping、error mapping、artifact route 或最终 output projection；
4. B 重算同一 artifact 后得到与 A 相同的业务结论，没有发现新输入问题。

实例：

- `claim_type_not_allowed → audit.passed=false → Section FAILED → formal=false → G40 writer/status/formal false → rejected`；
- `upstream CRAG irrelevant → G04 rejected_by_final_crag_irrelevant / eligibility=false`；
- `G14 technical call/parse/contract failure → classification missing → G15 semantic_unclassified`；
- `upstream citations unavailable → G19 bindings=[] → G23 citation_bound=false`；
- `cross_section_fact_conflict → repair task BLOCKED → conflict_repairs_resolved=false`；
- `G36 required_section_missing → G37 原样复制同 code`。

### 16.2 Independent Failure

满足：即使 A 为 true，B 仍可使用不同输入独立失败。实例：

- G14 技术执行成功时，合法 classification 仍可因低置信度形成独立 `CLAIM_CLASSIFICATION` Root；
- Claim Audit pass 且 citation candidates 非空时，G19/G38 Citation 仍可独立失败；
- Citation pass 时，G22 High-risk exact fact support 仍可失败；
- 所有 Section checks pass 时，G34 cross-section fact comparison 仍可失败；
- G36 assembly pass 时，G37 仍可发现 Prompt leak/营销语言/重复正文；
- Hard Gate pass 后，G48 persistence/hash/manifest 仍可发生 TECHNICAL failure。

### 16.3 同 family 不等于同 event

两个不同 citation occurrence 各自 orphan，是两个 Root Events，但同属 `CITATION` family。相反，一个 occurrence 同时使 marker/binding bijection、orphan marker、required section 等多个 checks false，仍可能只有一个 Root Event。实际 event 去重键必须包含稳定实体身份，例如 section/sentence/claim/occurrence/conflict id，而不能只看 family 或 failure message。

## 17. Phase 1/2 discrepancy

冻结文档未修改。Phase 3 按“首次业务失败事实”发现以下口径精化：

1. **G05 双重角色**：Phase 2 把 G05 总体列为 AGGREGATED；代码中的 `_conflicts()` 实际首次创建 `EvidenceConflictSchema`，该 conflict event 是 ROOT，而 `EvidenceSetAssessment.status` 仍是 AGGREGATED。
2. **G14/G15 业务/技术 Root 边界**：必须先查 G14 call records。若 call/parse/items/id/retry outcome 技术失败，Root 是 G14 TECHNICAL，G15 `semantic_unclassified_substantive_claim` 是 DERIVED fail-closed manifestation；只有 G14 技术成功后的合法空分类、低置信或其他分类质量不达标，才由 G15 形成 `CLAIM_CLASSIFICATION` 业务 Root。`claim_type_not_allowed` 仍是独立 `CLAIM_POLICY` Root。
3. **G23 `model_success` 可达性**：`SectionQualityEvaluator.evaluate()` 内该 hard check 固定为 true；G18 模型失败在进入 G23 前早退，并自行写 `checks.model_success=false`。因此 Section model Root 的首次状态点是 G18，不是 G23。
4. **G35 BLOCKED 边界**：有效 target 的 repair task BLOCKED 机械来自 G34 conflict，属于 DERIVED；只有 unknown target 等独立 contract 异常另属 TECHNICAL。
5. **G37 上游复制边界**：assembly validation 失败时 G37 原样复制 G36 failure，是 DERIVED；只有 G37 自己扫描出的 final-text issue 是 ROOT。
6. **G43 审批请求边界**：显式 require approval 与 interrupt 是独立 workflow decision/state，不是业务 Root Failure；真正的人工业务拒绝 Root 在 G44。
7. **G04 eligibility 边界**：`rejected_by_final_crag_irrelevant` 直接消费上游 `crag_final_judgement.relevance=irrelevant`，故 G04 `eligibility=false` 是 DERIVED；G04 自身 project/structure/fact/authority/source-form/semantic-threshold rule 首次拒绝时才是 `EVIDENCE_ELIGIBILITY` Root。
8. **G19 availability/grounding 边界**：`citations=[] → bindings=[]` 只能说明 G19 无输入，Root 必须追到上游 availability；仅当 candidates 非空并经 `bind_citations()` / `supported_bindings()` 后仍无 verified binding，G19 才形成 `CITATION` grounding Root。

这些精化不改变 G01–G50 编号，也不改写 Phase 1/2 文件。

## 18. Phase 3 事实结论

1. Independent Decision 数、Control 数、violation 数、false check 数、Root Event 数是五种不同计数。
2. G02 correction exhausted 与 G03 prompt-missing carry 都不是 Root Business Failure。
3. Evidence block 可以通过 PARTIAL diagnostic Section 进入 formal/hard-gate 拒绝，不要求 Section 先变 FAILED。
4. Claim violation 是最清晰的一对多传播：孤立 `claim_type_not_allowed` 为 1 个 Root，可在 G40形成 5 个 false checks，并最终投影为 rejected 与 need review。
5. `writer_claim_audit_recomputed_valid=true` 只说明失败 audit 可被重算复现；不说明 audit 通过。
6. `writer_formal_eligibility_recomputed=true` 可表示 false 与 false 一致；它不等于 formal eligible。
7. Citation、High-risk fact 与 Claim policy 是独立检查，可在同一 Section 同时形成多个 Root Events。
8. Section FAILED 至少有 Model、Quality、Citation、Claim、Paragraph、Budget 六类可能来源，不能反推单一根因。
9. Human Review 风险状态、formal 条件、error metadata、workflow interrupt、最终 output projection 是不同链；只有 G43 真正 interrupt。
10. G32 result-level need review 是聚合镜像；G39 直接读取 Gate HR 与 Section extra need HR，而不是该 result 字段。
11. G25 是第一次 formal 投影，G39 是 authoritative recomputation，G39 equality 是 consistency check，G40 是文档聚合，G47/G48 是发布前提与发布完整性。
12. G40/G41 `passed=false` 只能说明至少一个输入失败；Root 数既可能少于 false checks，也可能多于一个。
13. G34 conflict 与 G35 unresolved repair 通常是同一个 Document Root 的两次表现；G36 fail 与 G37 mirror 同理。
14. rejected 有两条业务来源：G41 hard-gate failure 或 G44 human rejection；technical_failure 是第三条独立技术路径。
15. G07/G09/G10/G14/G16/G46/G48 等技术异常不进入业务 Root Family 统计，也不伪造新的业务 Hard Gate Root；其下游 business manifestation 仍保留技术 provenance。
16. G04 `eligibility=false` 具有双重归因：`rejected_by_final_crag_irrelevant` 是上游 CRAG relevance Root 的 DERIVED 投影；G04 local policy/relevance 首次拒绝才是 `EVIDENCE_ELIGIBILITY` Root。
17. G14 technical classifier failure 与 G15 classification quality failure 必须二选一追溯最早来源：前者使 G15 semantic_unclassified 成为 DERIVED；技术成功后的低置信/合法空分类才形成 `CLAIM_CLASSIFICATION` Root。
18. `bindings=[]` 不等于 G19 grounding Root：`citations=[]` 时追上游 availability；candidates 非空且 binding/support 校验拒绝时才是 G19 `CITATION` grounding Root。

Phase 3 的归因原则是：先按 Earliest-Failure Principle 定位最早首次失败事实，再沿稳定实体身份去重 downstream projections，最后才按 Root Family 汇总；不得从最终 false、failure 数量反推根因数量。
